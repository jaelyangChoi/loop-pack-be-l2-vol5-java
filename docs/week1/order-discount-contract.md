# 주문 쿠폰 할인 — 설계 기록 (W1)

모호한 쿠폰 요구 한 줄을, 다른 엔지니어가 반례와 출처를 따라갈 수 있는 약속으로 바꾼다.
제품 코드(`apps/commerce-api/src/main/**`)는 바꾸지 않는다. W2 에서 이 문서를 테스트와 코드로 옮긴다.

---

## 0. 기준 문장과 출처

> **"구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고, 확정된 할인 금액은 나중에 바뀌지 않아야 합니다."**

- **출처**: Loopers 1주차 실습 과제 정의(Notion). 확정된 제품 약속으로 주어진 문장이다.
- 이 문장 하나만으로는 "만료 시각을 언제 기준으로 보는지", "같은 요청을 다시 보내면 어떻게 되는지",
  "누가 이 쿠폰을 적용할 수 있는지"가 정해지지 않는다. 아래에서 사실 / 실습 전제 / 질문으로 나눈다.

## 1. 기존 동작 관찰 (Example API)

`ContractClassificationTest`(`apps/commerce-api/src/test/java/com/loopers/interfaces/api/ContractClassificationTest.java`)로
실제 HTTP 요청을 보내 확인한 `/api/v1/examples/{id}` 의 현재 계약. 주문 할인 API 의 오류 계약을 정할 때 기준선이 된다.

| 입력 | HTTP status | `meta.result` | `meta.errorCode` | `data` | `meta.message` |
|---|---|---|---|---|---|
| 존재하는 숫자 ID | `200 OK` | `SUCCESS` | `null` | 객체 | `null` |
| 숫자가 아닌 ID (`abc`) | `400 Bad Request` | `FAIL` | `"Bad Request"` | `null` | `요청 파라미터 'exampleId' (타입: Long)의 값 'abc'이(가) 잘못되었습니다.` |
| 존재하지 않는 숫자 ID (`-1`) | `404 Not Found` | `FAIL` | `"Not Found"` | `null` | `[id = -1] 예시를 찾을 수 없습니다.` |
| 미매핑 URL (`/api/v1/no-such-resource`) | `404 Not Found` | `FAIL` | `"Not Found"` | `null` | `존재하지 않는 요청입니다.` |

**관찰에서 눈에 띄는 점**

- 응답 포맷: 최상위 `meta` + `data`. `meta.result` 는 문자열(`"SUCCESS"` / `"FAIL"`), `data` 는 실패 시 항상 `null`.
- `meta.errorCode` 는 커스텀 코드가 아니라 **HTTP reason phrase 문자열**(`"Not Found"` 등)이라 HTTP status 와 항상 1:1 이다.
- 그래서 **"존재하지 않는 도메인 리소스"와 "아예 매핑 안 된 URL"이 status·errorCode 로는 구분되지 않고**
  (`404 / "Not Found"`) `meta.message` 로만 갈린다. 두 상황이 사실상 한 응답으로 합쳐진다.
- 사용 가능한 `ErrorType` 은 `INTERNAL_ERROR(500)`, `BAD_REQUEST(400)`, `NOT_FOUND(404)`, `CONFLICT(409)` 뿐이다.
  `FORBIDDEN(403)` 은 없다.

## 2. 요구사항 분류

### 2-1. 확인된 사실 (제품 약속)

기준 문장에서 직접 근거를 찾을 수 있는 것만.

| # | 내용 | 근거 (기준 문장의 어느 부분인가) |
|---|---|---|
| F-1 | 구매자는 주문이 **확정되기 전**에 자신이 보유한 쿠폰을 주문에 적용할 수 있다. | "구매자는 주문 확정 전에 보유 쿠폰을 적용할 수 있고" |
| F-2 | 주문이 확정되면 그 시점의 할인 금액은 **이후에 바뀌지 않는다**. | "확정된 할인 금액은 나중에 바뀌지 않아야 합니다" |

### 2-2. 이번 과제에서만 적용하는 실습용 전제

실제 정책으로 확정된 게 아니라 이번 실습 범위를 좁히려는 임시 조건. 틀렸을 때 무엇을 되돌려야 하는지도 적는다.

| # | 내용 | 틀렸을 때 되돌릴 지점 |
|---|---|---|
| P-1 | 한 주문에는 쿠폰을 **한 장만** 적용한다. | 다중 쿠폰 스택 규칙, 적용 API 의 `couponId` 배열화, 합산·우선순위 계산 |
| P-2 | `finalAmount = originalAmount - discountAmount` (단일 식, 정액 차감). | `discountAmount` 계산기(정률·최대 한도·반올림 정책), 응답 필드 구조 |
| P-3 | 같은 요청(같은 주문 + 같은 쿠폰)의 결과는 재사용한다(멱등). | 재요청 시 재계산/거부 여부, 멱등 키 저장소, 응답 캐시 |
| P-4 | 쿠폰 만료 판단은 **요청 시작 시각** 기준으로 한다. | 만료 기준 시각(적용 시점 vs 확정 시점), 처리 지연 중 만료 재검증 로직 |

### 2-3. 제품 담당자에게 확인할 질문

각 질문이 답에 따라 **사용자 응답 / 저장 데이터 / 권한** 중 무엇을 바꾸는지 연결한다.

| # | 질문 | 답에 따라 달라지는 것 |
|---|---|---|
| Q-1 | 쿠폰 적용 시점엔 유효했지만 주문 확정 시점엔 만료된 경우, 확정을 막는가 아니면 적용 시점 판정을 유지하는가? | **사용자 응답** — 확정 단계에서 새로 오류를 보게 되는지가 달라진다 |
| Q-2 | 주문이 취소·실패하면 사용한 쿠폰을 되돌려 주는가? | **저장 데이터** — 쿠폰 사용 상태(사용됨/복구됨) 저장 방식이 달라진다 |
| Q-3 | 운영자가 구매자를 대신해 쿠폰을 적용·해제할 수 있는가? | **권한** — 적용 API 를 호출할 수 있는 주체가 달라진다 |
| Q-4 | 할인 금액이 주문 원금보다 클 때 `finalAmount` 를 0원으로 막는가, 아니면 그 쿠폰 적용 자체를 거부하는가? | **사용자 응답** — 0원 성공 vs 오류 |
| Q-5 | 확정 전에 이미 적용한 쿠폰을 다른 쿠폰으로 교체하거나 해제할 수 있는가? | **저장 데이터** — 주문에 붙은 쿠폰 슬롯을 변경 가능 상태로 둘지 |

### 2-4. 출처 없는 제안

| 제안 | 판정 | 이유 |
|---|---|---|
| "보유 쿠폰 중 할인액이 가장 큰 쿠폰을 자동 선택해 적용" | **거절** | 기준 문장·실습 전제·기존 코드 어디에도 근거 없음. 이번 범위는 요청이 `couponId` 를 명시적으로 지정하는 것으로 한정한다. |
| 그 외 도구가 별도로 제안한 제품 정책 | **해당 없음** | 없음 |

## 3. 불변식과 반례 (`INV-001` ~ `INV-006`)

W2 에서 같은 뜻으로 쓸 규칙. 각 행에 반례를 하나씩 연결한다.
출처 구분: **제품 약속**(F-*) · **실습 조건**(P-*) · **제품 질문**(Q-*, 답이 나와야 확정되는 규칙).

| 규칙 ID | 출처 구분 | 규칙 내용 | 깨지는 입력 (반례) | 기대 결과 | 책임 후보 |
|---|---|---|---|---|---|
| `INV-001` | 제품 약속 (F-1) | 구매자는 **본인 주문**에 **본인이 보유한 쿠폰**만 적용할 수 있다. | 다른 사용자가 소유한 `couponId` 로 적용 요청 | 적용 거부, 주문·쿠폰 상태 변화 없음 | 주문·쿠폰 소유권 검증 (application Facade) |
| `INV-002` | 제품 약속 (F-2) | 확정된 주문의 `discountAmount` / `finalAmount` 는 이후 재계산·변경되지 않는다. | 확정 후 쿠폰 할인율 또는 원금이 바뀌고 주문을 재조회 | 확정 시점에 저장된 값을 그대로 반환 | 확정 시 금액 스냅샷 저장 (domain Model) |
| `INV-003` | 실습 조건 (P-1) | 확정 전 한 주문에는 쿠폰이 최대 한 장 붙는다. | 이미 쿠폰이 적용된 주문에 두 번째 쿠폰 적용 요청 | 두 번째 요청 거부 (교체 허용 여부는 Q-5) | 주문의 쿠폰 슬롯 관리 (domain Model) |
| `INV-004` | 실습 조건 (P-2) | `finalAmount = originalAmount - discountAmount` 이고 `finalAmount >= 0` 이다. | `discountAmount > originalAmount` 인 쿠폰 적용 | `finalAmount` 0 으로 고정 또는 적용 거부 (Q-4) | 할인 금액 계산 (domain) |
| `INV-005` | 실습 조건 (P-3) | 같은 주문 + 같은 쿠폰으로 온 재요청은 저장된 결과를 돌려주고 효과를 중복 적용하지 않는다. | 동일 요청을 연속 2회 전송 | 첫 결과와 동일한 응답, 쿠폰 차감·할인 반영은 1회만 | 멱등 처리 (application Facade + 저장 계층) |
| `INV-006` | 실습 조건 (P-4) | 만료 여부는 **요청 시작 시각**으로 판정한다. | 쿠폰 만료 시각이 "요청 시작"과 "저장 완료" 사이에 지나감 | 요청 시작 시각 기준으로 유효하다고 판정, 적용 성공 | 시각 기준 검증, `Clock` 주입 (domain) |

## 4. 외부 API 계약과 내부 책임 경계

### 4-1. 외부 API 계약

| 항목 | 값 |
|---|---|
| Method / Path | `POST /api/v1/orders/{orderId}/discount` |
| 사용자 식별 | 요청 주체(구매자)의 식별자. **기존 `example` 도메인에는 인증 장치가 전혀 없다** — W2 에서 헤더(`X-USER-ID` 등) 또는 토큰 중 하나로 확정해야 하며, 지금은 "요청에서 구매자 식별자를 얻을 수 있다"고 가정하고 Q-3 과 함께 남긴다. |
| Request Body | `{ "couponId": <long> }` (적용할 쿠폰을 명시적으로 지정). `originalAmount` 는 요청에서 받지 않고 주문에서 조회한다. |
| 성공 응답 (`200`) | `meta.result = "SUCCESS"`, `data = { orderId, originalAmount, discountAmount, finalAmount }` |

**오류별 외부 의미** (기존 `ApiResponse` 포맷과 `ErrorType` 재사용, `errorCode` 는 HTTP reason phrase)

| 상황 | HTTP | `meta.result` | `meta.errorCode` | `data` | 요청자의 다음 행동 |
|---|---|---|---|---|---|
| `couponId` 타입 오류 | `400` | `FAIL` | `Bad Request` | `null` | 요청 형식 수정 후 재시도 |
| `couponId` 누락 | `400` | `FAIL` | `Bad Request` | `null` | 필드 추가 후 재시도 |
| 존재하지 않는 `orderId` | `404` | `FAIL` | `Not Found` | `null` | 주문 번호 확인 |
| 존재하지 않는 `couponId` | `404` | `FAIL` | `Not Found` | `null` | 쿠폰 확인 |
| 타인 소유 쿠폰 / 본인 주문 아님 (`INV-001`) | `404` | `FAIL` | `Not Found` | `null` | 재시도하지 않음 (아래 결정 1 참고) |
| 만료된 쿠폰 (`INV-006`) | `409` | `FAIL` | `Conflict` | `null` | 다른 쿠폰 선택 |
| 이미 쿠폰이 적용된 주문 (`INV-003`) | `409` | `FAIL` | `Conflict` | `null` | 기존 쿠폰 해제 후 재시도 (Q-5) |
| 이미 확정된 주문 (`INV-002`) | `409` | `FAIL` | `Conflict` | `null` | 변경 불가 |
| 할인액 > 원금이고 정책상 거부 (`INV-004`, Q-4) | `409` | `FAIL` | `Conflict` | `null` | 다른 쿠폰 선택 |

> 기본 시나리오(`POST /api/v1/orders/{orderId}/discount`, body 에 `couponId`)를 그대로 따른다. 차이 없음.

### 4-2. 규칙별 책임

| 책임 | 보장해야 하는 상태 / 행동 | 관련 규칙 |
|---|---|---|
| 주문 상태 확인 | 주문이 아직 확정 전이다 | `INV-002` |
| 소유권 확인 | 주문·쿠폰이 요청 구매자의 것이다 | `INV-001` |
| 쿠폰 슬롯 확인 | 주문에 이미 쿠폰이 없다 | `INV-003` |
| 만료 확인 | 요청 시작 시각 기준으로 쿠폰이 유효하다 | `INV-006` |
| 할인 계산 | `finalAmount = originalAmount - discountAmount`, 음수 없음 | `INV-004` |
| 결과 저장 | 확정 시 금액을 스냅샷으로 저장, 재요청은 같은 결과 | `INV-002`, `INV-005` |

### 4-3. 세 가지 설계 결정

**결정 1. 오류를 어떻게 구분하고 표현할 것인가**

- **선택한 방식**: 기존 `ApiResponse` 포맷을 그대로 쓰고, 도메인 오류(만료·중복 적용·확정됨·정책 거부)는 모두 `409 Conflict` 로,
  소유권 위반은 `404 Not Found` 로 매핑한다(리소스 존재 자체를 숨긴다). 세부 구분이 필요하면 `meta.message` 로 전달한다.
- **버린 대안**: `COUPON_EXPIRED`, `ORDER_ALREADY_CONFIRMED` 같은 도메인 전용 `errorCode` 체계를 새로 만든다.
- **이유**: 기존 관찰에서 이미 "존재하지 않는 리소스"와 "미매핑 URL"이 `404 / "Not Found"` 로 합쳐져 있다.
  W1 단계에서는 계약의 안정성이 우선이고, 클라이언트가 실제로 분기 처리가 필요하다고 확인되면 W2 이후 코드 체계를 넓힌다.

**결정 2. snapshot 저장 vs 재계산**

- **선택한 방식**: 주문 확정 시 `discountAmount`, `finalAmount`, 적용된 `couponId` 를 주문에 **스냅샷으로 저장**한다.
- **버린 대안**: 주문을 조회할 때마다 그 시점의 쿠폰 정책으로 할인을 **재계산**한다.
- **이유**: `F-2`(확정된 할인 금액 불변). 쿠폰 할인율이나 주문 원금이 나중에 바뀌어도 확정 값은 그대로여야 한다.
  재계산 방식은 이 불변식을 구조적으로 깬다.

**결정 3. 조회 → 계산 → 저장까지의 호출 순서를 어느 경계가 숨길 것인가**

- **선택한 방식**: `POST /api/v1/orders/{orderId}/discount` **한 번의 호출**로 application Facade 가
  주문 조회 · 소유권/상태/만료 검증 · 할인 계산 · 결과 저장을 한 트랜잭션에서 오케스트레이션한다. 외부에는 최종 결과만 노출한다.
- **버린 대안**: 클라이언트가 "쿠폰 검증 API → 할인 계산 API → 확정 API" 를 순서대로 호출한다.
- **이유**: 호출 순서와 부분 실패 처리의 복잡도를 서버가 흡수한다. 계산식(`P-2`)이 바뀌어도 외부 계약은 그대로다.
  멱등(`INV-005`)도 서버가 한 경계 안에서 보장할 수 있다.

## 5. 다음 단계 (W2)

- **질문 확정**: Q-1 ~ Q-5 를 제품 담당자에게 확인한다. 특히 Q-1(만료 경계)과 Q-4(음수 금액)는 규칙(`INV-004`, `INV-006`)의
  기대 결과를 바꾸므로 먼저 답을 받는다.
- **규칙 이관**: `INV-001` ~ `INV-006` 을 domain / service 통합 테스트로 옮긴다(`규칙 ID / 입력 / 기대 결과 / 책임 후보` 기준).
- **사용자 식별 방식 확정**: 기존 `example` 에 없는 인증/식별 장치를 어떤 방식으로 넣을지 정한다.
- **`ErrorType` 확장 여부**: 결정 1 을 유지할지, 도메인 전용 코드를 추가할지 클라이언트 요구를 보고 결정한다.
