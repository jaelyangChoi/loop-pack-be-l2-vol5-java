# 캐시 설계·구현 참고 노트 (4주차)

> `발제.md`의 캐시·무효화·장애 대응 부분을 사례 중심으로 풀어 정리한 참고 자료입니다.
> AI에게 설계·구현을 맡길 때 **반례와 점검 기준**으로 사용합니다. 여기 적힌 방식을 그대로 구현하라는 지시가 아니며, 어떤 캐시를 둘지는 측정 결과를 본 뒤 정합니다.

## 0. 한 장 요약

| 주제 | 핵심 |
| --- | --- |
| TTL | "저장 시점"부터 센다. 변경 후 TTL 이내 최신이라고 단정할 수 없다 |
| 낡음의 상한 | 진행 중이던 요청의 지연 + 복제 지연 + TTL |
| 커밋 경계 | `@Transactional`은 MySQL만 묶는다. Redis는 별개이며 rollback이 없다 |
| 무효화 시점 | DB commit **이후**. 단, Redis 실패는 여전히 남는다 |
| 캐시 범위 | 많이 캐시할수록 지울 곳이 늘어난다 |
| revision 방식 | 낡은 캐시를 지우지 않고 구분한다. hit에도 DB 조회 1회가 남는다 |
| Spring 캐시 | 프록시 한계, `@CacheEvict` 시점 보장 없음 |
| Redis 연결 | `REPLICA_PREFERRED`는 무효화 직후 옛 값을 읽을 수 있다 |
| Redis 장애 | DB 우회는 **정상 응답**이어야 한다. 빈 값·0원으로 바꾸지 않는다 |
| 개선 주장 | 실제 원본 호출이 줄었는지 SQL 수로 증명한다 |

## 1. 낡은 값이 보이는 원인 (오래된 읽기, 지연된 복제본)

> TTL을 30초로 뒀다고 "변경 후 반드시 30초 안에 모든 요청이 최신"이라고 말할 수 없다.

### 1-1. 오래된 DB 읽기가 늦게 완료되는 경우

변경 **전**에 DB를 읽은 요청이, 변경과 캐시 삭제가 끝난 **뒤에** 낡은 값을 캐시에 저장한다.

```
t=0초   요청 A: cache miss → DB 조회 → 10,000원 (이후 GC·락 대기 등으로 지연)
t=1초   관리자: 가격 12,000원 commit → 캐시 삭제 (정상 수행)
t=5초   요청 A 재개: 들고 있던 10,000원을 캐시에 SET (TTL 30초)
t=5~35초  모든 조회가 10,000원  ← DB는 이미 12,000원
```

- 삭제는 성공했지만 이미 출발한 요청이 삭제 뒤에 낡은 값을 도로 넣었다.
- A가 오래 멈출수록 낡은 기간이 늘어난다. 상한은 `A의 지연 + TTL`.

### 1-2. 지연된 복제본에서 다시 채워지는 경우

복제본(replica)은 원본의 사본이며, 원본에 쓴 내용이 도착하기까지 시간차(복제 지연)가 있다.

```
t=0초   원본 DB: 12,000원 commit, 캐시 삭제 성공
t=0.5초 요청 B: cache miss → 복제본 조회 → 아직 10,000원 (복제 지연 2초)
t=0.5초 B가 10,000원을 캐시에 SET (TTL 30초)
t=2초   복제본에 12,000원이 도착했지만 캐시는 이미 낡은 값으로 채워짐
```

### 1-3. 낡음의 상한 공식

```
낡은 값이 보이는 최대 시간 ≈ (진행 중 요청의 지연) + (복제 지연) + TTL
```

설명할 때는 "보통 TTL 이내, 경쟁이 나면 이만큼 더 길어질 수 있다"처럼 **조건을 붙인다.**

## 2. 커밋 경계와 Redis 경계

```
MySQL 경계: @Transactional 안에서 commit/rollback 으로 원자성 보장
Redis 경계: 트랜잭션 밖. rollback 없음. 명령 하나하나가 즉시 반영
```

한 메서드 안에서 두 저장소를 건드려도 **함께 성공하거나 함께 실패하지 않는다.**

### 2-1. commit 전에 캐시를 지우면 안 된다

```java
@Transactional
public void changePrice(long id, long price) {
    productService.changePrice(id, price);   // UPDATE (commit 전)
    cache.evict(id);                         // Redis 즉시 삭제
}                                            // ← 여기서 commit
```

```
t=1  관리자: 캐시 삭제 (commit 전)
t=2  조회: miss → DB 조회 → commit 전이라 옛 값 10,000원 → 캐시에 저장
t=3  관리자: commit (DB는 12,000원)  → 캐시에 10,000원이 TTL 동안 남음
```

### 2-2. commit 이후에 무효화한다

```java
// 방법 1: 트랜잭션 동기화
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            // 여기서 던진 예외는 이미 확정된 commit 을 되돌리지 못한다.
            // 캐시 삭제 실패는 직접 catch 해서 로그·메트릭으로 남긴다.
            cache.evict(id);
        }
    });

// 방법 2: 이벤트 + AFTER_COMMIT 리스너
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void on(ProductChanged event) {
    cache.evict(event.productId());
}
```

### 2-3. after-commit으로도 남는 실패

| 상황 | 올바른 처리 |
| --- | --- |
| commit 이후 Redis 삭제 실패 | 예외를 삼키고 로그·메트릭. **"변경 실패"로 응답하지 않는다** (DB는 이미 확정) |
| 그 뒤의 낡은 값 | TTL이 마지막 방어선. 허용하는 낡음의 범위를 명시 |
| 더 강한 신선도 필요 | 재시도, 버전(revision) 검증, 또는 캐시 대상에서 제외 |

### 2-4. 한눈에 보는 실패 유형

```
정상:  DB commit → 캐시 삭제 성공            → 다음 조회 최신
실패:  DB commit → 캐시 삭제 실패            → TTL까지 낡은 값
경쟁1: 캐시 삭제 → (다른 조회가 낡은 값 채움) → DB commit      ← after-commit 으로 해결
경쟁2: 조회 A가 낡은 값 읽음 → 변경·삭제 → A가 저장            ← after-commit 으로도 남음
```

### 2-5. 프로젝트 구조에서의 점검

- `Admin*Facade`의 `@Transactional` 안에서 캐시를 직접 지우지 않는다.
- ArchUnit 규칙상 `application`은 `infrastructure`에 의존할 수 없다. 캐시는 `domain`에 포트 인터페이스를 두고 `infrastructure`에서 구현한다.
- Redis 실패가 DB 변경 응답을 깨지 않는지 테스트한다.

## 3. 관리자 변경과 캐시 범위

DB는 한 행만 바뀌어도 캐시에는 그 값이 들어간 **복사본이 여러 곳**에 있다.

### 3-1. 영향 사례

캐시 키 예시.

```
products:v1:detail:id=7
products:v1:brand=3:sort=price_asc:page=0:size=20
products:v1:brand=3:sort=price_asc:page=1:size=20
products:v1:brand=3:sort=price_desc:page=0:size=20
```

| 변경 | 영향받는 캐시 |
| --- | --- |
| 상품 7 가격 9,000 → 25,000 | 상세 `id=7`, 가격순 목록(순서·구성이 바뀜), 다른 페이지로 넘어가는 항목 |
| 상품 생성 | 목록 1페이지 구성, 전체 건수(45 → 46), 마지막 페이지 |
| 상품 삭제 | 목록에 남은 상품이 클릭하면 404가 되는 불일치 |
| 브랜드 이름 변경·일괄 삭제 | 그 브랜드의 모든 상품 목록·상세 키. 삭제 상품이 계속 노출될 수 있음 |
| 좋아요 등록·취소 | 좋아요 수, 좋아요순 정렬(동점 순서), **사용자별 "내가 좋아요" 표시** |
| 재고 변경·주문 확정 | 응답에 재고가 있으면 낡은 표시 (판단에는 캐시를 쓰지 않는다) |

좋아요는 자주 일어난다. 매번 목록 캐시를 지우면 캐시가 거의 비어 있게 되므로 **허용 신선도를 정하는 판단**이 필요하다.

### 3-2. 범위와 무효화 책임

| 캐시 선택 | 무효화 부담 |
| --- | --- |
| 상품 상세만 | 상세 키 하나. 단순 |
| 목록 첫 페이지만 | 정렬 종류만큼의 키. 적당 |
| 모든 목록 페이지 | 거의 모든 변경이 영향. 어려움 |

**캐시 범위를 작게 고르면 무효화 책임도 작아진다.** 재사용이 적은 깊은 페이지까지 저장하면 hit는 적고 지울 키만 늘어난다.

### 3-3. 무효화 방식 선택

1. **관련 키만 삭제**: miss 최소. 조합(브랜드×정렬×페이지)이 늘면 빠뜨리기 쉽다.
2. **전용 캐시 영역 통째로 비우기**: 빠뜨릴 걱정이 없다. 직후 전부 miss → DB 몰림(stampede). 이 비용을 **측정해서 기록**한다.
3. **공유 Redis 전체 비우기(`FLUSHALL`)**: 사용하지 않는다. 다른 기능의 데이터까지 날린다.

### 3-4. 설계 전에 채울 표

| 캐시 후보 | 응답에 포함된 필드 | 영향을 주는 변경 | 무효화 대상 |
| --- | --- | --- | --- |
| (예) 상품 상세 | 이름·가격·브랜드명·좋아요 수 | 상품 수정·삭제, 브랜드 변경, 좋아요 | 상세 `id=N` |
| (예) 브랜드별 목록 1페이지 | 위와 동일 | 위 + 상품 생성 | `brand=B` 목록 |

"이 변경이 이 키에 영향을 주는지 모르겠다"가 나오는 곳은 캐시 대상에서 빼거나 TTL로 낡음을 허용하기로 정한다.

### 3-5. 키 설계 주의

- 키는 응답을 구분하는 조건이다: 브랜드·필터, 정렬·페이지·크기, 응답 형식 버전.
- 사용자별 정보("내가 좋아요했는지")를 공용 캐시에 섞지 않는다. 별도로 합성한다.
- 키에 `v1`을 붙이는 것만으로 DB 변경을 감지하지 못한다.

## 4. revision 방식 (선택지 하나, 필수 아님)

> 낡은 캐시를 **지우려 하지 않고**, 낡은 캐시를 **읽지 않도록 번호로 구분**한다.

### 4-1. 구조

Product 테이블은 건드리지 않는다. **별도의 작은 테이블**에 캐시 묶음(scope)별 revision을 둔다. PK는 scope이다.

```sql
CREATE TABLE cache_revision (
    scope    VARCHAR(50) PRIMARY KEY,
    revision BIGINT NOT NULL
);
INSERT INTO cache_revision VALUES ('product-catalog', 1);
```

캐시 키마다 행을 두지 않는다. 목록 키는 조합으로 무한히 늘어나기 때문이다.

### 4-2. 쓰기: 같은 트랜잭션에서 올린다

```java
@Transactional
public void changePrice(long productId, long price) {
    productService.changePrice(productId, price);   // products UPDATE
    catalogRevisionService.bump();                  // cache_revision UPDATE
}                                                   // 함께 commit
```

payload를 바꾸는 **모든 쓰기**(생성·삭제·브랜드·좋아요 등)가 `bump()`에 참여해야 한다. 하나라도 빠지면 그 경로의 변경은 조용히 반영되지 않는다.

### 4-3. 읽기: DB의 revision을 먼저 읽는다

```java
public ProductListView findList(Query q) {
    long rev = catalogRevisionRepository.current("product-catalog");  // DB, PK 1행

    String key = "products:rev=%d:brand=%d:sort=%s:page=%d"
                     .formatted(rev, q.brandId(), q.sort(), q.page());

    var cached = cache.find(key);
    if (cached.isPresent()) return cached.get();      // hit: 비싼 쿼리 없음

    ProductListView result = readRepository.findList(q);   // miss
    cache.save(key, result, ttl);                          // rev 가 박힌 키에 저장
    return result;
}
```

### 4-4. 늦게 끝난 낡은 조회가 문제를 못 일으키는 이유

```
t=0   A: revision 41 확인 → 조회 (10,000원) → 지연
t=1   관리자: 가격 12,000 + revision 42 commit
t=5   A 재개 → 낡은 결과를 rev=41 키에 저장
t=6   B: revision=42 → rev=42 키 miss → DB 조회 → rev=42 키에 저장
```

A가 채운 곳은 `rev=41` 키라 B는 읽지 않는다. 옛 키는 TTL로 정리된다.

### 4-5. 반드시 지킬 계약

| 규칙 | 어기면 |
| --- | --- |
| revision을 **Redis가 아니라 DB**에서 읽는다 | Redis의 포인터가 낡으면 폐기된 데이터를 계속 읽는다 |
| miss에서 결과와 revision을 **같은 일관된 읽기**로 얻는다 | 옛 결과가 새 revision 키에 들어간다 |
| payload를 바꾸는 모든 쓰기가 참여한다 | 빠진 경로는 반영되지 않는다 |
| 고정된 잠금 순서, 기존 rollback 규칙 유지 | 데드락 |

### 4-6. 비용

- hit에도 DB 조회 1회(PK). 0회가 아니다.
- 모든 쓰기가 같은 revision 행을 갱신하므로 **행 락 경합**이 생긴다. 좋아요처럼 고빈도 쓰기를 참여시키면 병목이 될 수 있다.
- scope를 `product-catalog` 하나로 두면 어떤 변경이든 전체 캐시가 무효화된다. 나누면 hit율은 오르지만 쓰기 쪽이 `bump()`를 여러 개 호출해야 한다.
- 비싼 목록·집계 쿼리를 줄인 시간과, revision 조회·락 경합으로 생긴 새 비용을 **따로 측정해 비교**한다.

### 4-7. 진행 중이던 요청의 해석

- 변경 **이전에 시작한** 조회: 그 조회가 읽은 DB 시점의 결과로 설명한다(오류가 아님).
- 변경 **완료 후 새로 시작한** 요청: 반드시 새 값.
- 테스트에서도 둘을 구분해 검증한다.

### 4-8. 언제 쓰나

| 요구 | 선택 |
| --- | --- |
| 장애 중에도 낡은 값을 절대 보여 주면 안 됨 | revision 방식 |
| 몇 초 낡음 허용 | TTL + commit 후 무효화. 허용 범위·복구 정책 명시 |

## 5. "개선"으로 인정되지 않는 캐시

### 5-1. 항상 DB를 조회한 뒤 안 쓰는 캐시를 채우기

```java
var cached = cache.find(key(q));
ProductListView fresh = readRepository.findList(q);   // 매번 비싼 쿼리
cache.save(key(q), fresh);
return fresh;                                          // 캐시 값은 사용하지 않음
```

- 요청마다 Redis 2회 + 비싼 DB 쿼리 1회. 캐시 도입 전보다 느리다.
- hit율 지표는 올라 보일 수 있으나 **원본 호출은 하나도 줄지 않았다.**
- 낡음이 불안해서 생기는 패턴이다. 정말 최신성이 필요하면 revision(가벼운 확인 + 실제 사용)이나 캐시 대상 제외를 택한다.

### 5-2. 반대쪽 함정

DB 호출 0회만을 위해 기존 계약을 포기하지 않는다.

- 삭제 상품 비노출
- 소유권(남의 데이터 비노출)
- 주문 금액·재고 판단 (캐시의 낡은 값으로 구매를 확정하지 않는다. 주문 확정은 DB에 보존한 금액과 기존 상품 상태·재고 규칙을 사용한다)

### 5-3. 방식 비교

| 방식 | hit 때 DB | 원본 호출 감소 | 평가 |
| --- | --- | --- | --- |
| 일반 cache-aside | 없음 | 큼 | 낡음을 TTL로 허용할 때 |
| revision | 가벼운 확인 1회 | 비싼 쿼리만 감소 | 낡음 불허. 가벼움을 측정으로 증명 |
| 항상 DB 조회 후 캐시 채우기 | 비싼 쿼리 매번 | 없음 | 개선 아님 |
| 캐시만 믿고 계약 무시 | 없음 | 큼 | 정확성 계약 위반 |

### 5-4. 확인 방법

- 캐시 hit 요청 한 번에 실행된 **SQL의 개수와 종류**를 본다. 기대값: 0개 또는 PK 조회 1개.
- 목록 집계 쿼리가 hit 요청에서 보이면 캐시가 원본 호출을 줄이지 못한 것이다.
- `OrderListQueryCountTest`처럼 SQL 개수를 테스트로 고정한다.

## 6. Spring 캐시 어노테이션과 Redis 읽기 연결

### 6-1. `@Cacheable`은 프록시 방식이다

```java
@Service
public class ProductService {
    public ProductView getDetail(long id) {
        return find(id);               // this.find() → 프록시 우회
    }

    @Cacheable("product")
    public ProductView find(long id) { // 내부 호출이라 캐시가 동작하지 않음
        return repository.find(id);
    }
}
```

- 같은 객체 내부 호출, `private`/`final` 메서드에는 적용되지 않는다. 에러 없이 조용히 동작하지 않는다.
- 해결: 캐시 메서드를 다른 빈으로 분리해 외부에서 호출한다.

### 6-2. `@CacheEvict`는 commit 이후라는 보장이 없다

기본 동작은 "메서드 정상 반환 직후 삭제"이며, `@Transactional` 프록시와의 순서에 따라 commit 이전에 삭제될 수 있다(2-1과 같은 경쟁). 실제 순서를 테스트·로그로 확인하거나 `afterCommit`에서 직접 삭제한다.

### 6-3. 캐시 오류 처리

Spring 캐시 추상화는 기본적으로 캐시 예외를 그대로 던진다. Redis 장애가 곧 API 오류가 되지 않도록 `CacheErrorHandler` 등으로 원본 조회 우회를 설정했는지 확인한다.

### 6-4. 이 프로젝트의 Redis 연결

`modules/redis/.../RedisConfig.java`에 두 연결이 있다.

| 연결 | `ReadFrom` | 템플릿 |
| --- | --- | --- |
| 기본 | `REPLICA_PREFERRED` | 기본 `RedisTemplate` |
| 별도 | `MASTER` | `redisTemplateMaster` |

### 6-5. 무효화 직후 replica가 옛 값을 줄 수 있다

```
t=0.000  master: DEL products:7        (성공)
t=0.001  기본 연결 GET products:7 → replica 선택 → 아직 삭제 미반영 → 옛 값
t=0.010  replica에 삭제 반영
```

- "변경 직후 최신인가"를 검증하는 실험에서는 **어느 연결로 읽었는지 명시**한다. 그렇지 않으면 실패 원인이 코드 버그인지 복제 지연인지 구분할 수 없다.
- 낡음을 약간 허용하는 목록: replica 선호 가능. 무효화 직후 정확해야 함: master 읽기.
- master로 읽어도 **DB·Redis 원자성은 생기지 않는다.** 복제 지연이라는 한 가지 원인만 제거한다.

## 7. Redis 장애 대응

> 캐시는 없어도 서비스가 정상 응답해야 하는 부가 장치다. 느려질 수는 있어도 틀린 답을 주면 안 된다.

### 7-1. 우회는 "원본 조회"이지 "기본값 반환"이 아니다

```java
// 잘못된 예: 빈 객체, 가격 0
catch (Exception e) { return ProductView.empty(); }

// 올바른 예: 캐시 장애만 잡고 원본으로 정상 응답
try {
    var cached = cache.find(id);
    if (cached.isPresent()) return cached.get();
} catch (CacheUnavailableException e) {
    metrics.cacheReadFailure();
}
return db.find(id);
```

### 7-2. 점검 항목

| 항목 | 설명 |
| --- | --- |
| 대기 시간 제한 | connect/command 타임아웃. 응답 없이 멈춘 Redis는 스레드 풀을 고갈시킨다 (설정값은 `redis.yml`·`RedisConfig`에서 확인 필요) |
| miss와 오류 구분 | miss는 정상, Redis 오류는 장애. 같은 `null`로 처리하면 장애를 못 알아챈다. 오류 메트릭을 따로 둔다 |
| DB 오류 비은폐 | `catch (Exception)`으로 크게 감싸 빈 결과를 주지 않는다. 잡을 것은 캐시 장애뿐이다 |
| 복구 후 낡은 항목 | 장애 중 변경의 삭제가 실패했다면 복구 후 옛 키가 부활한다. TTL 단축, 실패 기록 후 재시도, 영역 비우기 중 무엇을 쓰는지 확인 |
| 중단 대상 | 테스트가 **실제로 연결한 endpoint**를 중단한다. 이 프로젝트의 테스트는 `RedisTestContainersConfig`의 별도 컨테이너에 붙으므로 Compose를 내려도 장애가 아니다 |

### 7-3. 장애 시 DB 부하

```
평소:  요청 1,000/s × hit 95% → DB 50/s
장애:  요청 1,000/s × hit 0%  → DB 1,000/s (20배)
```

DB 응답이 느려지면 연결 풀 고갈 → 연결 대기 증가 → 모든 API 지연으로 번진다. 기능적 fallback만으로는 충분하지 않을 수 있다. 동시 요청 제한·부하 축소는 다음 판단이며, 이번에는 **작은 통제 부하**에서 다음을 확인한다.

- 우회 응답이 정상 시와 같은가
- 지연이 얼마나 늘었는가
- DB 연결 대기가 눈에 띄게 늘었는가

### 7-4. Cache stampede

같은 항목의 miss가 동시에 발생해 원본 조회가 몰리는 현상.

```
인기 키 TTL 만료 → 요청 300건이 동시에 miss → 같은 SELECT 300번 → DB 급증
```

| 원인 | 예 |
| --- | --- |
| 인기 키 만료 | 초당 1,000건 조회되는 키의 TTL 종료 |
| 같은 시각 만료 | 한꺼번에 채워 TTL이 같음 |
| 무효화 직후 | 영역 통째로 비운 직후 |
| Redis 재시작 | 캐시 전체가 비어 있음 |

대안: 요청 합치기(같은 키는 한 요청만 DB 조회), TTL 분산(`30초 ± 랜덤`). 여러 서버의 분산 잠금은 복잡도가 높으므로 모든 캐시에 먼저 도입하지 않는다.

정확성 문제(오래된 읽기)와 달리 stampede는 **값은 맞지만 DB가 과부하**되는 가용성 문제다.

## 8. 검증 시나리오 모음

| 장면 | 확인할 결과 |
| --- | --- |
| 인덱스 전후 | 같은 업무 결과, 계획·읽은 행·시간의 변화 |
| cache miss/hit | 동일 입력에서 응답 일치, **실제 원본 호출 감소**(SQL 수) |
| 정상 관리자 변경 | 선택한 캐시와 영향 범위가 최신 값 반영 |
| 무효화 실패·경쟁 | 낡은 값의 재현, 허용 범위 또는 방지 장치, 복구 결과 |
| Redis 장애·재시작 | 제한된 대기와 DB 우회, 복구 후 정확한 재채움 |
| 영역 비우기 | 직후 DB 쿼리 수·지연이 얼마나 튀는지 기록 |

오래된 읽기 재현은 `CountDownLatch` 등으로 "조회가 DB를 읽은 뒤 멈춤 → 변경·삭제 → 조회 재개" 순서를 강제하면 된다.

## 9. AI에게 설계·구현을 맡길 때의 체크리스트

1. 보존할 계약(필터·정렬·페이지·응답 필드·삭제 노출 규칙)과 관찰한 병목(SQL 계획, 요청당 SQL 수)을 먼저 준다. "Redis를 붙여 줘"로 시작하지 않는다.
2. 캐시 후보마다 3-4의 표(응답 필드 → 영향 변경 → 무효화 대상)를 채우게 한다.
3. 무효화는 **commit 이후**에 있는가, Redis 실패가 DB 변경 응답을 깨지 않는가 확인한다.
4. 허용하는 낡음의 범위와 상한(1-3의 공식)을 문장으로 적게 한다.
5. 캐시 장애와 DB 장애를 구분해서 잡는가, 빈 값·0원 반환이 없는가 확인한다.
6. hit 요청의 SQL 수를 테스트로 고정해 "장식 캐시"가 아님을 증명한다.
7. 읽기 연결(replica/master)과 테스트가 중단하는 endpoint를 명시한다.
8. 캐시로 줄인 비용과 늘어난 운영 책임(무효화·장애 처리)을 함께 기록한다. DB 쿼리 개선만으로 충분했다면 캐시를 추가하지 않는다.
9. 범위 밖 개편(주문 단가 결정 시점 변경, 삭제 상품 복원, 페이지 API를 커서로 교체 등)은 하지 않는다. 정책·검사 기준 변경이 필요하면 이유와 영향을 설명하고 확인을 받는다.
