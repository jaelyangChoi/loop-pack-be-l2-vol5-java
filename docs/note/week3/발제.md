## 🧩 브랜드는 사라졌는데 상품은 남았다

2주차에는 삭제되지 않은 상품이 남은 브랜드의 삭제를 거절했습니다. 이번에는 **브랜드를 삭제할 때 연결된 상품도 함께 고객의 사용 대상에서 제외하는 기능**으로 확장합니다. 재고가 0인 상품도 대상이고, 다른 브랜드의 상품이나 과거 주문은 바꾸지 않습니다.

브랜드 B에 상품 P1·P2가 있다고 합시다. 브랜드 변경을 저장하고 P1까지 처리한 뒤 P2를 저장하다 실패했습니다. 앞의 변경이 이미 확정됐다면 고객은 남아 있는 P2의 브랜드를 찾지 못합니다.

| 상태 | 브랜드 B | 상품 P1 | 상품 P2 | 판단 |
| --- | --- | --- | --- | --- |
| 작업 전 | 사용 가능 | 사용 가능 | 사용 가능 | 일관된 시작 상태 |
| 일부만 반영 | 삭제·비노출 | 삭제·비노출 | 사용 가능 | 브랜드와 상품의 상태가 어긋남 |
| 성공 | 삭제·비노출 | 삭제·비노출 | 삭제·비노출 | 의도한 일괄 결과 |
| 중간 실패 후 | 작업 전 상태 | 작업 전 상태 | 작업 전 상태 | 이번 변경 전체가 취소됨 |

각 저장 메서드가 올바르더라도 **유스케이스 전체의 성공**은 보장되지 않습니다. 이때 필요한 것이 트랜잭션입니다.

### 📧 트랜잭션과 commit·rollback

> **DB 트랜잭션**은 여러 읽기·변경을 하나의 성공 또는 실패로 다루는 작업 단위입니다.
>
1. **시작**: 처리에 필요한 DB 작업을 한 트랜잭션 안에서 수행합니다.
2. **commit**: 트랜잭션의 변경을 성공한 결과로 확정합니다.
3. **rollback**: 확정하지 않은 변경을 취소합니다.

```
트랜잭션 시작
  브랜드 확인 → 연관 상품 확인 → 상품들 변경 → 브랜드 변경
                                   │
                 정상 종료 ───────┼─→ commit
                 중간 실패 ───────┴─→ rollback
```

실패 후에 반대 SQL을 차례로 보내는 방식은 rollback과 다릅니다. 복구 SQL 자체도 실패할 수 있고, 다른 요청의 변경을 덮어쓸 수 있습니다. **하나의 DB에서 함께 확정할 변경은 먼저 같은 트랜잭션으로 묶는 것**이 출발점입니다.

트랜잭션은 DB의 변경을 되돌립니다. 이미 전송한 HTTP 요청, 보낸 메시지나 파일까지 자동으로 취소하지는 않습니다. 지금의 브랜드·상품과 포인트 주문은 같은 DB 안의 변경이므로 로컬 트랜잭션으로 설명할 수 있습니다.

### 🧱 ACID가 보장하는 것과 구현이 맡는 것

| 성질 | 의미 | 브랜드·상품 사례에서 볼 것 |
| --- | --- | --- |
| **Atomicity · 원자성** | 작업을 전부 반영하거나 전부 취소 | 상품 일부만 바뀐 상태를 성공으로 남기지 않음 |
| **Consistency · 일관성** | 정한 제약과 규칙을 만족하는 상태 사이에서 변경 | 사용 가능한 상품이 삭제된 브랜드를 참조하지 않음 |
| **Isolation · 격리성** | 동시 트랜잭션이 서로를 보는 방식과 간섭을 제어 | 다른 요청의 변경을 언제 읽고 언제 기다리는지 |
| **Durability · 지속성** | commit한 결과를 장애 뒤에도 보존 | DB의 로그·저장 및 내구성 설정에 따라 확정 결과 복구 |

DB는 외래 키·유일성 같은 선언된 제약을 검사하지만, “이 브랜드의 모든 상품을 함께 내려야 한다”는 규칙을 스스로 알아내지는 않습니다. **업무 규칙과 트랜잭션 경계는 구현이 정해야 합니다.**

commit은 백업을 대신하지도 않습니다. 지속성의 보장 범위는 저장 장치와 DB 설정에 의존하므로, 로컬 테스트 성공을 모든 장애에서의 데이터 보존 증명으로 확대하지 않습니다.

## 🗑️ 삭제의 의미와 일괄 변경의 범위

2주차에 구분한 Hard delete와 Soft delete는 여기서도 선택의 기준입니다.

| 방법 | 일괄 처리에서 필요한 판단 | 과거 주문에 대한 영향 |
| --- | --- | --- |
| **물리 삭제** | 참조를 정리한 뒤 실제 행 제거가 가능한가? | 상품 삭제가 Order·OrderItem까지 지우지 않도록 참조 정책 확인 |
| **논리 삭제·비노출** | 행은 남기고 사용 가능 여부를 어떻게 판정하는가? | 주문의 저장된 상품 정보·단가·금액은 유지하고 새 사용은 거절 |

핵심은 저장 방법의 통일이 아니라 **없애려는 대상과 보존할 사실을 구분하는 것**입니다. 이번 일괄 처리에서 참조를 유지해야 한다면 논리 삭제·비노출이 자연스럽습니다. 물리 삭제를 선택한 기존 모델이라면 주문의 저장 정보와 참조가 안전한지 먼저 확인합니다.

- **함께 변경**: 해당 브랜드와 연결된 미삭제 상품 전체. 재고 0인 상품도 포함합니다.
- **그대로 보존**: 다른 브랜드·상품, 기존 주문 품목·수량·단가·총액·포인트 결제 결과.
- **변경 후 거절**: 삭제된 상품의 고객 상세·새 좋아요·새 주문, 상품 수정·재고 변경.
- **기존 DRAFT 주문**: 생성만 했다고 구매 가능성이 예약된 것은 아닙니다. 확정 시 상품이 삭제됐다면 거절합니다.

<aside>
⚠️

**연쇄 삭제는 업무 판단을 대신하지 않습니다.**

외래 키의 cascade로 주문까지 함께 지우면 트랜잭션은 그 잘못된 결과를 원자적으로 commit할 수도 있습니다. “모두 함께 바뀐다”와 “올바른 것을 바꾼다”는 별도 조건입니다.

</aside>

과거 주문 조회에서 현재 상품 가격을 다시 읽어 금액을 계산하면 상품 수정이 과거 결제액을 바꿉니다. 이미 저장한 **주문 당시의 정보와 금액**을 조회해야 합니다. 현재 상품은 판매 대상이고 주문 품목은 그때의 거래 사실이라는 차이입니다.

일괄 처리가 한 트랜잭션이라는 사실만으로 다른 요청의 상품 추가까지 막힌 것은 아닙니다. 같은 브랜드의 관리 작업을 동시에 허용한다면 대상 집합을 보호하는 규칙도 필요합니다. 먼저 이번 기능의 **중간 실패 원자성**을 확인하고, 동시 실행이 추가하는 질문을 구분합니다.

## 🌱 Spring·JPA에서 실제 경계 찾기

### 🔀 프록시를 통과해야 적용되는 규칙

Spring의 기본 프록시 방식에서는 컨테이너가 관리하는 객체 앞의 프록시가 호출을 받아 트랜잭션을 시작하거나 기존 트랜잭션에 참여시킵니다.

```
Controller → Spring proxy → Application service → Repository → DB
             시작/참여         업무 흐름 실행          │
             commit/rollback ← 정상 반환 또는 예외 ──┘
```

브랜드·상품 repository 각각의 저장에만 트랜잭션이 있으면 두 저장이 별도로 commit될 수 있습니다. **함께 실패해야 할 유스케이스의 호출 경계**를 먼저 묶어야 합니다. 모든 서비스에 annotation을 붙이는 것보다, 어떤 DB 작업이 같은 물리 트랜잭션에 참여하는지 확인하는 편이 중요합니다.

- Java · 자기 호출에서 놓치는 경계

  아래는 프록시 함정을 보여 주는 구조 예시입니다. 완성된 삭제 기능이 아닙니다. 호출자가 Spring의 `WrongBoundary` bean을 통해 `remove`를 호출하고 바깥 트랜잭션이 없다고 가정합니다.

    ```java
    @Service
    class WrongBoundary {
        public void remove(long brandId) {
            removeTogether(brandId); // 같은 객체의 직접 호출
        }
    
        @Transactional
        public void removeTogether(long brandId) {
            // 브랜드·상품 변경
        }
    }
    ```

  `removeTogether`의 annotation은 자기 호출에 새로 적용되지 않습니다. 외부에서 호출되는 `remove`에 경계를 두거나, 별도 Spring bean의 트랜잭션 메서드를 호출하는 구조로 바꿉니다. 이미 바깥 트랜잭션이 있다면 내부 작업은 그 경계 안에서 실행될 수 있으므로 “자기 호출이면 언제나 트랜잭션이 없다”는 설명도 정확하지 않습니다.

- Kotlin · 같은 경계와 프록시 설정

  외부에서 Spring bean을 통해 호출되는 유스케이스에 경계를 둡니다. 다음은 annotation 위치를 보여 주는 구조 예시입니다.

    ```kotlin
    @Service
    class BrandApplicationService {
        @Transactional
        fun removeTogether(brandId: Long) {
            // 브랜드 확인 → 연관 상품 변경 → 브랜드 변경
        }
    }
    ```

  annotation의 import는 `org.springframework.transaction.annotation.Transactional`입니다. Kotlin 클래스·메서드는 기본적으로 final이므로 기존 `kotlin("plugin.spring")` 적용을 확인합니다. JPA의 생성자·엔티티 설정과 Spring 프록시 설정도 구분합니다. Java·Kotlin 모두 같은 객체 안의 직접 호출 문제는 같습니다.


### ↩️ 예외가 생겼을 때 무엇이 취소되는가

기본 rollback 규칙을 별도로 바꾸지 않았다면 다음과 같습니다.

| 메서드 밖으로 전달된 결과 | Spring의 기본 처리 | 주의할 점 |
| --- | --- | --- |
| 정상 반환 | commit 시도 | flush·commit 단계에서 실패할 수도 있음 |
| RuntimeException | rollback | 예외를 잡고 정상 반환하면 같은 의미가 아님 |
| checked exception | 기본적으로 rollback 대상 아님 | 필요한 예외에 `rollbackFor` 등 명시적 규칙 적용 |
| Error | rollback 대상 | JVM 종료·자원 고갈에서 복구 완료까지 보장한다는 뜻은 아님 |

상품 변경 도중 생긴 예외를 catch한 뒤 “일부 실패” 값만 반환하면 프록시가 정상 종료로 판단할 수 있습니다. 반대로 이미 참여 중인 작업이 rollback-only로 표시했다면 catch해도 마지막 commit에서 실패할 수 있습니다. **예외 타입·전달 방식·최종 DB 상태**를 함께 확인해야 합니다.

### 🔗 전파: 같은 트랜잭션인가, 별개인가

| 전파 | 의미 | 브랜드·상품 일괄 변경에서의 판단 |
| --- | --- | --- |
| **REQUIRED** | 기존 트랜잭션에 참여하고, 없으면 시작 | 같은 DB·트랜잭션 관리자에서 함께 성공·실패할 작업에 사용 |
| **REQUIRES_NEW** | 바깥 트랜잭션을 보류하고 별도 트랜잭션 실행 | 상품별로 쓰면 앞 상품이 따로 commit되어 전체 rollback 요구를 깨뜨릴 수 있음 |
| **NESTED** | 지원되는 자원에서 savepoint를 사용 | DB·트랜잭션 관리자 지원을 확인해야 하며 JPA에서 무조건 가능한 중첩 트랜잭션이 아님 |

메서드가 중첩됐다고 물리 트랜잭션도 중첩되는 것은 아닙니다. `REQUIRED`로 참여한 내부 작업이 실패하면 바깥의 전체 변경까지 취소될 수 있습니다. `REQUIRES_NEW`는 별도 commit과 추가 connection 비용을 갖기 때문에, 실패를 피하려고 무작정 분리할 옵션이 아닙니다.

### 🧺 영속성 컨텍스트, flush와 commit

JPA는 조회한 엔티티를 **영속성 컨텍스트**에서 관리하고 변경 감지로 SQL을 보낼 수 있습니다.

- **객체 변경**: 메모리의 관리 중인 엔티티가 바뀝니다.
- **flush**: 변경 SQL을 DB에 보냅니다. **commit은 아닙니다.**
- **commit**: 트랜잭션 결과를 확정합니다. 그 전에 flush가 일어날 수 있습니다.
- **clear**: 관리 중인 엔티티를 분리합니다. DB rollback을 뜻하지 않습니다.

같은 엔티티를 다시 읽어 값이 바뀌었다고 DB commit까지 증명된 것은 아닙니다. 실패 테스트에서는 앞의 변경 SQL이 실제 전송되도록 flush한 뒤 예외를 일으키고, **트랜잭션 종료 후 새 경계에서 재조회**해 rollback을 확인합니다.

- 보충 · 반복 변경과 bulk UPDATE

  상품이 적은 실습에서는 엔티티를 조회해 행동을 호출하는 방식이 이해하기 쉽습니다. JPQL·native bulk UPDATE는 여러 행을 한 문장으로 바꿀 수 있지만 엔티티별 행동·콜백·변경 감지 경로와 같지 않습니다.

  이미 읽어 둔 객체와 DB가 달라질 수 있으므로 필요한 변경을 먼저 flush하고, bulk 변경 뒤에는 해당 객체를 재조회하거나 영속성 컨텍스트를 정리하는 방법을 판단합니다. 무조건 clear하면 아직 보내지 않은 변경을 잃을 수 있습니다. bulk 사용 자체를 과제의 필수 조건으로 삼지는 않습니다.


`@Transactional(readOnly = true)`는 읽기 의도와 최적화를 위한 힌트이지, 모든 DB·JPA 구성에서 쓰기를 금지하는 보안 장치가 아닙니다. 삭제처럼 상태를 바꾸는 유스케이스에는 쓰기 경계를 사용합니다.

## 👥 트랜잭션 두 개가 같은 상태를 읽는다면

한 요청의 rollback을 확인했다면 다음 질문은 **서로 다른 요청이 동시에 성공해도 되는가**입니다.

재고가 5개인 상품을 두 요청이 각각 1개씩 주문합니다. 둘 다 5를 읽고 계산한 4를 저장하면 두 주문이 성공했는데 재고는 1개만 줄어듭니다. 한 갱신이 다른 갱신에 덮인 **Lost Update(갱신 유실)**입니다. 최종값이 음수가 아니어도 잘못될 수 있습니다.

| 순서 | 요청 A | 요청 B |
| --- | --- | --- |
| 1 | 재고 5 읽기 |  |
| 2 |  | 재고 5 읽기 |
| 3 | 계산한 4 저장·commit |  |
| 4 |  | 계산한 4 저장·commit |
| 결과 | 성공 2건 | 최종 재고 4 |

요청마다 `@Transactional`이 있어도 **읽은 값을 판단하고 쓰는 사이의 경쟁**을 자동으로 해결하지는 않습니다. 애플리케이션의 `synchronized`도 프로세스가 다르면 공유되지 않으며, 전역 잠금은 서로 다른 상품까지 기다리게 만듭니다.

### 🪟 격리 수준과 MVCC

> **격리 수준**은 동시에 실행되는 트랜잭션이 다른 변경을 어느 정도 관찰할 수 있는지 정하는 규칙입니다.
>

| 읽기 현상 | 뜻 | 작은 예 |
| --- | --- | --- |
| **Dirty Read** | 아직 commit하지 않은 변경을 읽음 | 다른 요청이 올렸다가 rollback한 가격을 봄 |
| **Non-repeatable Read** | 같은 행을 다시 읽었을 때 값이 달라짐 | 같은 트랜잭션에서 상품 가격이 두 번 다르게 보임 |
| **Phantom Read** | 같은 조건을 다시 조회했을 때 행 집합이 달라짐 | 가격 조건에 맞는 상품이 다른 요청의 추가로 늘어남 |

`READ UNCOMMITTED → READ COMMITTED → REPEATABLE READ → SERIALIZABLE` 순으로 격리가 강해지지만 비용과 실제 동작은 DB·SQL에 따라 다릅니다. `SERIALIZABLE`도 실패·재시도 처리를 없애는 옵션은 아닙니다.

**MVCC**는 데이터의 여러 버전을 이용해 읽는 시점에 맞는 결과를 제공하는 방식입니다. MySQL InnoDB의 기본 `REPEATABLE READ`에서는 일반적인 비잠금 SELECT가 같은 트랜잭션의 스냅샷을 읽습니다. `READ COMMITTED`의 일반 SELECT는 문장마다 새 스냅샷을 사용합니다.

그러나 **일반 SELECT와 잠금 읽기·UPDATE는 같은 방식으로 동작하지 않습니다.** InnoDB의 잠금 읽기와 범위 잠금도 고려해야 하므로 “REPEATABLE READ면 어떤 SQL에서도 모든 경쟁이 사라진다”거나 단순한 현상 표만으로 갱신 안전성을 판단하면 안 됩니다. 실제 SQL과 보호할 행·조건을 함께 봅니다.

### 🔒 비관적 잠금: 판단 전에 대상 보호하기

재고를 읽을 때 쓰기 잠금을 얻고 트랜잭션이 끝날 때까지 유지합니다. 다른 쓰기 요청은 기다렸다가 **잠금을 얻은 뒤의 현재 상태**로 판단해야 합니다.

```sql
SELECT quantity
FROM stock
WHERE product_id = :productId
FOR UPDATE;
```

`stock`과 컬럼 이름은 SQL 설명용입니다. 현재 모델의 매핑에 맞춥니다.

- **적합한 경우**: 짧은 구간에 같은 재고·잔액 충돌이 자주 발생합니다.
- **비용**: 잠금 대기, connection 점유, 교착 가능성이 생깁니다.
- **주의**: 보호 범위는 실행 계획·인덱스·조건에 따라 달라집니다. 일반적인 비잠금 읽기까지 모두 막는다는 뜻은 아닙니다.

JPA의 `PESSIMISTIC_WRITE`를 선택해도 **잠금 조회와 변경이 같은 트랜잭션**에 있어야 합니다. 조회 직후 별도 트랜잭션이 끝나 잠금이 풀린다면 뒤의 판단을 보호하지 못합니다.

### 🔍 낙관적 잠금: 오래된 변경을 거절하기

엔티티에 `@Version`을 두면 읽었던 버전이 여전히 같은지 갱신 시 확인할 수 있습니다.

```sql
UPDATE stock
SET quantity = :newQuantity, version = version + 1
WHERE product_id = :productId AND version = :readVersion;
```

두 요청이 같은 버전을 읽었어도 먼저 성공한 요청이 버전을 바꾸면 나머지는 충돌을 감지합니다. 실제 SQL과 예외 발생 시점은 JPA 구현·flush 시점에 따릅니다.

- **적합한 경우**: 충돌이 드물고, 충돌을 명확히 알리거나 다시 시도할 수 있습니다.
- **비용**: 실패한 작업을 다시 읽고 계산하는 비용이 있습니다.
- **주의**: DB 쓰기 잠금이 전혀 없다는 뜻이 아닙니다. stale version을 거절하는 방식입니다.

재시도한다면 **실패한 트랜잭션 밖에서 새 트랜잭션으로 다시 읽고 판단**합니다. 같은 객체의 오래된 값으로 UPDATE만 반복하거나, rollback된 경계 안에서 예외를 삼키고 계속하면 안 됩니다. 횟수·대기·종료 조건을 정하고 충돌과 재고 부족을 구분합니다.

### ➖ 조건부 갱신: 검사와 차감을 한 SQL로

단순 수량 차감은 현재 값의 조건을 갱신 문장에 넣을 수 있습니다.

```sql
UPDATE stock
SET quantity = quantity - :requested
WHERE product_id = :productId AND quantity >= :requested;
```

양수 수량을 먼저 검증하고, 대상 행이 하나인 경우 영향 행 수가 1이면 차감됐다고 판단합니다. 0이면 조건을 만족하지 못했거나 대상이 없는 것이므로 기존 오류 계약에 맞게 구분합니다.

**SQL 한 문장의 원자성과 주문 전체의 원자성은 다릅니다.** 재고 차감이 성공한 뒤 포인트가 부족하면 앞의 재고 차감도 취소되어야 합니다. 조건부 SQL을 선택해도 재고·포인트·주문을 묶는 트랜잭션은 필요합니다.

### ⚖️ 무엇을 선택할 것인가

| 전략 | 충돌을 다루는 방식 | 먼저 확인할 질문 |
| --- | --- | --- |
| 비관적 잠금 | 기다린 뒤 보호된 최신 상태로 판단 | 잠금 시간이 짧은가? 획득 순서가 일관적인가? |
| 낙관적 잠금 | 버전 충돌을 감지해 거절·재시도 | 충돌을 얼마나 허용하는가? 재시도 비용과 한도는? |
| 조건부 갱신 | SQL 조건과 영향 행 수로 판정 | 규칙을 한 문장으로 명료하게 표현할 수 있는가? |

재고에는 비관적 잠금, 다른 편집 기능에는 낙관적 잠금처럼 대상별로 선택할 수도 있습니다. 다만 같은 행을 바꾸는 경로 중 하나가 보호 규칙을 우회하면 안전하지 않습니다. **주문 차감뿐 아니라 포인트 충전과 관리자 재고 설정**이 어떤 방식으로 함께 참여하는지도 확인합니다.

## 🛒 재고·포인트·주문을 함께 지키기

기존 주문 생성은 DRAFT를 저장하고 차감하지 않습니다. **최초 확정**에서 상품 사용 가능 여부·재고·포인트를 확인하고, 차감과 CONFIRMED 변경·결제 결과 저장을 함께 처리합니다.

```
본인 주문 확인
  → 같은 DB 트랜잭션
     주문 상태 확인
     필요한 상품·재고·포인트 상태 보호 및 검증
     재고 차감 + 포인트 차감 + 확정 결과 저장
  → 모두 commit 또는 모두 rollback
```

불변식은 행 하나가 아니라 성공한 업무와 연결합니다.

- **재고**: `초기 재고 − 성공 주문의 품목 수량 합 = 최종 재고`
- **포인트**: `초기 잔액 + 성공 충전액 합 − 성공 결제액 합 = 최종 잔액`
- **주문**: 실패한 확정은 DRAFT이고, 성공한 확정만 CONFIRMED·결제 결과를 갖습니다.
- **요청 집계**: `성공 + 업무 거절 + 기술 오류 = 전체 요청`

동일 사용자의 서로 다른 주문이 서로 다른 상품을 사더라도 **같은 포인트 잔액**을 바꿉니다. 상품별 잠금만으로는 잔액을 보호하지 못합니다. 주문의 DRAFT 검사도 상태 변경과 분리해 보호 없이 먼저 끝내면 동시에 같은 주문을 처리할 수 있습니다.

### 🔁 여러 행과 교착 상태

A는 상품 1을 잠근 뒤 상품 2를 기다리고, B는 상품 2를 잠근 뒤 상품 1을 기다릴 수 있습니다. 서로가 가진 자원을 기다리는 상태가 **교착(deadlock)**입니다.

1. 같은 종류의 여러 행은 식별자 오름차순처럼 **일관된 순서**로 처리합니다.
2. 주문·포인트·재고처럼 종류가 다른 자원도 유스케이스들 사이의 획득 순서를 맞춥니다.
3. 잠금 구간에서 불필요한 조회·오랜 계산·외부 호출을 줄입니다.
4. DB가 중단한 트랜잭션은 종료하고, 재시도가 필요하면 새 경계에서 제한적으로 실행합니다.

순서를 맞추면 교착 위험을 줄일 수 있지만 모든 교착이 사라진다고 단정할 수는 없습니다. 잠금 시간 초과나 교착을 모두 “품절”로 바꾸면 운영 원인을 잃습니다. **업무상 거절과 기술적 실패는 복구 방법이 다릅니다.**

## 🧪 실패와 경쟁을 테스트로 구분하기

### ↩️ 중간 실패 뒤 실제 DB 다시 읽기

브랜드와 상품이 정상적으로 함께 바뀌는 테스트만으로 rollback을 알 수는 없습니다.

1. 브랜드·연관 상품·다른 브랜드 상품·기존 주문을 준비하고 commit합니다.
2. 실제 일괄 변경 경로에서 첫 변경을 DB에 보낸 뒤 테스트 설정으로 다음 저장에 예외를 발생시킵니다.
3. 예외가 트랜잭션 밖까지 전달되어 종료되는지 확인합니다.
4. **새 트랜잭션 또는 별도 connection**으로 읽어 전체가 작업 전 상태인지 확인합니다.

테스트 메서드 자체의 자동 rollback 때문에 값이 되돌아간 것을 서비스의 rollback이라고 오인하지 않습니다. 실패 주입은 테스트 구성에 두고 운영 코드에 실패용 API·sleep·공개 switch를 만들지 않습니다.

### 🏁 경쟁의 재현과 실제 서비스의 검증

시작 latch는 여러 작업을 비슷한 시각에 출발시킬 뿐, 같은 재고를 읽었다는 보장은 아닙니다. 그래서 두 가지를 나눕니다.

| 실험 | 확인하는 것 | 실행 방법 |
| --- | --- | --- |
| **깨진 읽기·쓰기 예제** | 갱신 유실의 원인 | 두 transaction이 5를 읽은 뒤 장벽을 풀고 각각 상수 4 저장 |
| **수정된 실제 서비스** | 선택한 제어와 주문 경계 | 시작만 맞춘 여러 요청이 실제 application·repository·DB를 통과 |

깨진 예제는 `성공 2 / 최종 재고 4`가 왜 틀린지 설명하는 테스트 전용 대조군입니다. 최종 테스트에서는 “이 잘못된 결과가 재현됐다”를 확인하고, 실패 assertion을 방치하거나 무시하지 않습니다. **그 대조군을 통과했다는 사실은 실제 주문의 정합성 증거가 아닙니다.**

- 공통 · 테스트 실행 구조
    - 초기 데이터는 worker 시작 전에 commit합니다. 각 worker는 독립된 connection·transaction으로 실제 Spring bean을 호출합니다.
    - executor와 connection 수는 실험의 동시 진입에 충분히 확보합니다. 2개 transaction 대조군에는 최소 2개가 필요합니다.
    - 준비 장벽·완료 future에는 제한 시간을 두고, timeout을 기대한 업무 거절로 세지 않습니다.
    - 예외를 출력만 하고 버리지 않고 요청별 결과를 수집합니다. 재고·잔액 부족, 충돌 한도 초과, 기술 오류를 구분합니다.
    - 모든 worker가 끝난 다음 새 DB 조회로 확인합니다. finally에서 대기를 풀고 executor·connection을 정리합니다.
    - `Thread.sleep`이나 반복 횟수 증가로 우연한 실패를 기다리지 않습니다. 테스트를 하나의 부모 transaction으로 감싸지도 않습니다.

초기 재고 5, 1개씩 사는 주문 8건, 모든 구매자의 충분한 포인트를 준비하면 **성공 5·재고 부족 3·최종 재고 0**을 기대할 수 있습니다. 낙관적 잠금에서 충돌 자체를 즉시 최종 거절하는 정책이라면 성공 수가 더 작을 수 있습니다. 아래 과제는 재고가 있는 요청을 한정된 재시도로 다시 판단하는 정책을 택하므로, 충돌 한도 초과를 품절로 섞지 않고 별도로 실패 원인을 확인합니다.

포인트 경쟁은 재고 부족과 분리합니다. 한 사용자의 잔액 10,000원에 서로 다른 4,000원 주문 3건, 충분한 재고를 준비하면 **확정 2·잔액 부족 1·최종 잔액 2,000원**입니다. 거절된 주문의 재고가 줄지 않았는지도 함께 확인합니다.

### 🤖 AI와 경계·반례 검토하기

먼저 트랜잭션 안의 읽기·변경, 보호할 행, 성공·실패의 기대 상태를 정합니다. 그다음 AI에게 **현재 코드에서 이 경계가 실제로 성립하는지** 묻습니다.

> **브랜드 일괄 변경과 주문 확정의 호출 흐름을 읽고, 프록시를 거치는 시작점·같이 rollback할 변경·잠금 순서를 설명해줘. 현재 설계를 깨뜨리는 중간 실패와 경쟁 순서를 하나씩 제안하고, 작은 수정안의 비용을 비교해줘.**
>

제안이 맞는지는 annotation 개수가 아니라 실제 호출과 SQL, 실패 뒤 재조회로 판단합니다. 재고 하나를 맞추려고 주문 상태·포인트 테스트를 지우거나, 테스트 전용 장벽을 제품에 넣는 변경은 받아들이지 않습니다.

2주차의 lint·ArchUnit은 유지하고 바뀐 경계와 관련된 테스트를 실행합니다. 도메인 수량 검사 모든 조합을 HTTP에서 반복할 필요는 없습니다. **rollback·잠금은 실제 DB 통합 테스트**, 접근·응답 연결은 필요한 HTTP 사례로 확인합니다.
