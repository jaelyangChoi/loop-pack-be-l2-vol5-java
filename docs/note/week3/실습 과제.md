## 💻 Implementation Quest

> **여러 변경을 하나의 성공·실패로 묶고, 동시 요청에서도 재고·포인트·주문이 함께 맞게 만듭니다.**
>

2주차에 구현한 브랜드·상품·포인트·주문 API와 repository, 테스트에서 이어갑니다. 재고나 주문 모델을 새로 만드는 과제가 아닙니다. 기존 패키지·도메인 책임과 로컬 사용자·관리자 구분을 유지하며 **브랜드 일괄 삭제·비노출, 중간 실패 rollback, 주문의 재고·포인트 경쟁**을 개선합니다.

### 📐 1. 변경 범위와 트랜잭션 설계

기존 설계 문서에 다음 세 흐름을 추가하거나 수정합니다.

| 흐름 | 같은 성공·실패로 묶을 것 | 보존할 것 |
| --- | --- | --- |
| 브랜드 일괄 삭제·비노출 | 브랜드와 연결 상품의 상태 변경 | 다른 브랜드·상품, 기존 주문 정보 |
| 최초 주문 확정 | 재고·포인트 차감, CONFIRMED 변경, 결제 결과 저장 | 실패한 주문의 DRAFT와 변경 전 재고·잔액 |
| 같은 재고·잔액의 동시 변경 | 읽기·검사·변경을 보호하는 행과 SQL | 성공한 업무와 최종 재고·잔액의 일치 |

**시작점·호출 경로·예외·잠금 순서**를 표시합니다. Controller부터 repository까지 실제 호출을 따라가며 어떤 Spring bean의 메서드가 프록시를 거치는지 확인합니다.

AI에는 현재 흐름과 기대 상태를 주고 자기 호출, 예외 삼키기, 독립 commit, 빠진 잠금 대상의 반례를 요청합니다. 선택한 트랜잭션 경계와 조정 전략의 이유를 정리한 뒤 작은 단위로 수정합니다. 2주차의 lint·ArchUnit과 AI 작업 규칙은 유지합니다.

### 🗑️ 2. 브랜드와 연관 상품의 일괄 처리

기존 `DELETE /api-admin/v1/brands/{brandId}`의 계약을 확장합니다. **연관 상품이 있으면 거절하던 동작을, 브랜드와 연결된 미삭제 상품을 함께 삭제·비노출 처리하는 동작으로 바꿉니다.**

| 기능 | 구현할 결과 | 핵심 조건 |
| --- | --- | --- |
| 일괄 삭제·비노출 | 브랜드와 연결된 미삭제 상품 전체가 고객의 사용 대상에서 제외됨 | 재고 0인 상품도 포함, 대상이 없으면 기존 없는 대상 오류 |
| 중간 실패 | 이번 요청의 브랜드·상품 변경이 전부 취소됨 | 일부 성공 응답을 반환하거나 상품마다 별도 commit하지 않음 |
| 고객·관리자 연결 | 삭제 대상은 고객 목록·상세·새 좋아요·내 좋아요 목록·새 주문에서 제외 | 기존의 자기 좋아요 취소는 유지, 삭제 대상 수정·재고 변경은 거절 |
| 기존 주문 보호 | 저장된 품목·수량·단가·총액·포인트 결제 결과가 그대로 조회됨 | 현재 상품 가격으로 재계산하거나 주문 행까지 연쇄 삭제하지 않음 |

물리 삭제·논리 삭제는 기존 설계와 참조에 맞게 선택합니다. 과거 주문이 현재 상품 행을 참조한다면 **참조를 남기고 사용 대상에서 제외하는 방식**을 먼저 검토합니다. DB의 cascade 설정만으로 업무 결과를 결정하지 않습니다.

- 연결 상품이 없는 브랜드도 정상 처리합니다.
- 다른 브랜드·상품은 변경하지 않습니다.
- 삭제 전에 생성된 DRAFT 주문도 확정 시 상품의 존재·삭제 여부를 다시 확인합니다.
- 일반·식별 없는 요청은 기존 관리자 접근 규칙으로 거절하며 DB를 바꾸지 않습니다.

**중간 실패 테스트**는 최소 한 번의 실제 변경 SQL이 나간 뒤 다음 저장 단계에 예외를 발생시키고, 트랜잭션 종료 후 별도 DB 조회에서 변경 전 상태를 확인합니다. 예외는 테스트 구성의 저장 경계에서 유발합니다. 이 테스트에서 앞 단계까지 전부 mock하면 DB rollback을 검증할 수 없습니다.

### 🛒 3. 기존 포인트 주문의 원자성과 경쟁 제어

주문 생성은 DRAFT를 저장하고 차감하지 않습니다. 기존 `POST /api/v1/orders/{orderId}/confirm`의 **최초 확정**을 개선합니다.

| 경계 | 구현할 것 |
| --- | --- |
| 주문·요청자 | 본인 주문인지, 아직 DRAFT인지 확인하고 상태 검사와 확정을 보호 |
| 상품·재고 | 상품 사용 가능 여부·총수량을 확인하고 성공한 품목만큼 차감 |
| 포인트 | 저장된 잔액을 확인하고 주문 결제액을 한 번 차감 |
| 확정 결과 | 재고·잔액·CONFIRMED·결제액·결과를 같은 DB 트랜잭션에 반영 |
| 실패 | 중간 오류·재고 부족·잔액 부족 시 부분 차감과 확정 결과를 남기지 않음 |

비관적 잠금·낙관적 잠금·조건부 갱신에서 **선택한 전략**을 실제 repository·SQL에 적용합니다. 낙관적 잠금에서 충돌을 다시 시도한다면 실패한 transaction을 끝내고 새 transaction으로 재조회·재판단하며 횟수와 대기 한도를 둡니다. 한도 초과를 재고·잔액 부족으로 바꾸지 않습니다.

- 여러 상품은 일관된 식별자 순서로 처리하고, 주문·포인트·재고의 보호 순서를 다른 변경 경로와 맞춥니다.
- 같은 포인트 행을 바꾸는 **충전·결제**, 같은 재고 행을 바꾸는 **관리자 최종 수량 설정·주문 차감**도 선택한 규칙을 우회하지 않게 합니다.
- 이미 CONFIRMED인 주문은 기존 상태 오류 계약으로 처리합니다. 새 요청키 체계나 성공 응답 재사용 기능을 추가하지 않습니다.
- JVM 전역 `synchronized`로 모든 상품을 직렬화하거나, 잠금 구간에 테스트용 장벽·sleep을 넣지 않습니다.

### 🧪 4. 실패·경쟁 결과 확인

**원인 설명용 재현**과 **개선된 실제 서비스 검증**을 구분합니다.

- 공통 · 갱신 유실을 재현하는 작은 대조군

  테스트 소스에서 독립된 transaction 두 개가 commit된 재고 5를 잠금 없는 SELECT로 읽게 합니다. 두 값이 5임을 확인한 다음 쓰기를 허용하고, 각 transaction은 읽어 둔 값에서 1을 뺀 **상수 4**를 조건·version 없이 저장합니다.

  두 commit 뒤 `성공 2 / 최종 재고 4`와 `2 + 4 ≠ 5`를 확인합니다. 이 결과가 틀린 이유를 설명하는 음성 대조군이며, 제품 구현이 아닙니다. 최종 테스트에서는 불변식 위반이 재현됐음을 assertion으로 확인하고 의도적인 실패를 방치하지 않습니다.

  `stock = stock - 1`인 SQL은 이 깨진 예제와 다릅니다. 두 번째 SQL의 “값이 실제로 바뀐 행 수” 차이를 업무 실패로 집계하지 않습니다. 두 읽기·쓰기 완료에는 제한 시간을 두고 최소 두 worker·connection을 확보합니다. timeout이나 SQL 오류는 갱신 유실 재현으로 세지 않습니다.

  이 post-read 장벽은 대조군 안에만 둡니다. 실제 잠금 서비스에는 넣지 않습니다.


실제 서비스는 worker의 **시작만 맞추고**, 각 요청이 독립된 transaction에서 현재 application·repository·MySQL을 통과하게 합니다. 요청별 성공·업무 거절·기술 오류를 수집하고 모든 worker가 종료된 뒤 DB를 다시 읽습니다.

| 검증 | 준비·실행 | 기대 결과 |
| --- | --- | --- |
| 브랜드 정상·실패 | 브랜드 1개, 연결 상품 2개(하나는 재고 0), 다른 브랜드 상품과 과거 주문 준비 | 정상은 대상 전체 제외. 중간 실패는 전체 원상태. 다른 대상·과거 주문은 두 경우 모두 유지 |
| 주문 정상·실패 | 여러 품목의 DRAFT 주문을 확정하고, 실제 변경 뒤 다음 단계에서 실패도 유발 | 정상은 전체 반영. 실패는 DRAFT·재고·잔액·결제 결과가 변경 전과 같음 |
| 재고 경쟁 | 재고 5, 1개씩 사는 서로 다른 DRAFT 주문 8개, 구매자별 충분한 잔액 | 확정 5·재고 부족 3·기술 오류 0·최종 재고 0. 확정된 주문의 수량·차감액만 반영 |
| 포인트 경쟁 | 한 사용자 잔액 10,000원, 서로 다른 4,000원 DRAFT 주문 3개, 충분한 재고 | 확정 2·잔액 부족 1·기술 오류 0·최종 잔액 2,000원. 거절된 주문의 재고는 유지 |
| 충전과 결제 | 잔액 10,000원에서 2,000원 충전과 7,000원 주문 확정을 함께 실행, 충분한 재고 | 두 요청 성공·기술 오류 0·최종 잔액 5,000원 |

재고 경쟁의 각 주문은 서로 다른 주문 ID를 사용합니다. 포인트 경쟁은 재고를 충분히 두어 **잔액 보호의 실패를 재고 부족이 가리지 않게** 합니다. 낙관적 충돌은 한정된 재시도로 현재 상태를 다시 판단하고, 한도를 넘었다면 별도로 기록해 위 기대 결과가 나오지 않은 원인을 확인합니다.

다음 식을 요청 결과와 DB의 주문·품목·잔액으로 함께 확인합니다.

- **수량**: 초기 재고 − 성공 주문의 품목 수량 합 = 최종 재고
- **잔액**: 초기 잔액 + 성공 충전액 합 − 성공 결제액 합 = 최종 잔액
- **집계**: 성공 + 업무 거절 + 기술 오류 = 전체 요청

<aside>
⚠️

**최종 재고가 음수가 아니라는 확인만으로 끝내지 않습니다.**

모든 요청을 거절하거나 성공 결과를 집계에서 빠뜨린 코드도 그 조건을 만족할 수 있습니다. 기술 오류를 품절·잔액 부족으로 숨기지 않습니다.

</aside>

- 공통 · DB 테스트 실행 시 주의할 점
    - 데이터는 worker 시작 전에 commit합니다. 테스트 전체를 하나의 부모 transaction으로 감싸지 않습니다.
    - rollback 확인은 서비스 transaction 종료 후 새 경계에서 재조회합니다. JPA의 같은 관리 객체만 다시 보는 것은 확인이 아닙니다.
    - 대기와 future에 제한 시간을 두고, finally에서 대기를 해제한 뒤 worker·executor·connection을 정리합니다.
    - 기존 MySQL fixture를 사용합니다. 메모리 DB나 repository mock은 실제 잠금·rollback의 증거를 대신하지 않습니다.

성공·실패의 HTTP 연결은 브랜드 일괄 처리와 주문 확정의 대표 사례로 확인합니다. **관리자·사용자 접근 경계와 기존 기본 기능은 유지**하되, 같은 수량 규칙의 모든 경계값을 모든 계층에 반복 작성할 필요는 없습니다.

다른 잠금 전략 비교, 재고 요청을 12개로 늘린 실험, 브랜드 삭제와 상품 등록의 동시 실행은 선택 확장입니다. 선택하지 않은 시나리오까지 검증됐다고 쓰지 않습니다.

### 📤 5. 실행·제출

현재 테스트 구조에 브랜드·주문 transaction/경쟁 테스트를 추가합니다. 아래 이름은 실행 예시이며 실제 작성한 테스트 이름으로 맞춥니다.

- 공통 · 기존 DB 지원 코드

  두 starter의 `modules/jpa/src/testFixtures`에 있는 다음 지원 코드를 참고합니다.

    - Java: `java/com/loopers/testcontainers/MySqlTestContainersConfig.java`, `java/com/loopers/utils/DatabaseCleanUp.java`
    - Kotlin: `kotlin/com/loopers/testcontainers/MySqlTestContainersConfig.kt`, `kotlin/com/loopers/utils/DatabaseCleanUp.kt`

  기존 설정은 MySQL 8.0 이미지를 사용합니다. DB 설정·정리 도구는 지원하지만, 브랜드 일괄 처리와 주문 경쟁 테스트를 완성해 제공하는 것은 아닙니다.

- 공통 · 관련 테스트 실행 예시

    ```bash
    ./gradlew :apps:commerce-api:test --tests '*BrandRemovalTransactionTest'
    ./gradlew :apps:commerce-api:test --tests '*OrderTransactionTest'
    ./gradlew :apps:commerce-api:test --tests '*OrderConcurrencyTest'
    ```

  실제 패키지·클래스 이름을 사용하고 실행 건수·실패·종료 결과를 확인합니다. 수정 중에는 관련 테스트로 확인하고, 완료 시 영향받는 기존 브랜드·상품·포인트·주문 테스트와 2주차 검사 설정을 함께 실행합니다.

- Java·Kotlin · 마무리 검사

    ```bash
    # Java: 2주차에 연결한 Checkstyle 포함
    ./gradlew :apps:commerce-api:check
    
    # Kotlin: 기존 ktlint와 테스트
    ./gradlew :apps:commerce-api:ktlintCheck :apps:commerce-api:check
    ```

  ArchUnit 테스트가 실제 변경 코드를 검사하는지도 확인합니다. 기존 로컬 실습 설정을 유지하고 공개 배포·실제 개인정보 사용은 하지 않습니다.


**제출**: 변경 코드·테스트, 갱신한 설계 문서와 기술 글을 제출합니다. PR에는 트랜잭션 경계·선택한 제어 방식·핵심 결과를 짧게 적고, 긴 원시 로그를 본문에 모두 복사하지 않습니다.

- [ ]  재고 경쟁·포인트 경쟁·충전과 결제의 성공·거절·기술 오류와 최종 DB 상태가 기대 결과와 맞는다.
