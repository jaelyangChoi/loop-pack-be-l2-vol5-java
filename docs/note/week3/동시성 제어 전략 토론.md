# 동시성 제어 전략 토론 정리 (칼럼 재료)

> 칼럼 본문이 아니라, 본문을 쓸 때 꺼내 쓰는 정리본이다. 아래 서술 중 **"가설"** 표시는 아직 실측하지 않은 내용이며, 구현 뒤 테스트와 SQL 로그로 확인해 고친다. 최종 결정은 `docs/design/week3/transaction-concurrency-design.md`의 D-23~D-29에 있다.

## 1. 토론의 출발점

week3 과제는 브랜드 일괄 삭제, 주문 확정의 재고·포인트 경쟁을 다룬다. 처음에는 "재고는 비관적 잠금인가 낙관적 잠금인가"로 시작했지만, 유스케이스를 하나씩 놓고 보니 질문이 바뀌었다.

토론에서 나온 문제 제기:

1. 유스케이스마다 전략이 달라야 하지 않을까? 브랜드 삭제는 연관 상품 삭제와 함께 다른 사용자의 주문, 브랜드에 상품을 추가하는 요청까지 고려해야 한다.
2. 포인트 충전과 결제는 동시에 일어날 가능성이 낮다. 낙관적 잠금으로 충분한가, 아니면 비관적 잠금을 써도 비용이 없는가?
3. 재고 차감은 여러 사용자의 경쟁에 관리자 재고 설정, 브랜드 삭제의 대량 UPDATE가 겹친다. 낙관적 잠금이면 트랜잭션이 너무 길어지지 않을까? 비관적 잠금이면 교착이 생기지 않을까?
4. 조건부 갱신이 더 맞는 경우는 없는가?

## 2. 먼저 드러난 사실: 경쟁은 "같은 행을 쓰는 모든 경로"에서 생긴다

Hibernate는 기본 설정에서 바뀌지 않은 컬럼까지 **전체 컬럼을 UPDATE**한다. 그래서 업무상 다른 필드를 바꾸는 요청끼리도 서로를 덮어쓴다.

| 순서 | 브랜드 삭제 T1 | 주문 확정 T2 | 결과 |
|---|---|---|---|
| 1 | 상품 P를 읽음 (재고 5, 삭제 안 됨) | | |
| 2 | | P를 읽음 (재고 5, 삭제 안 됨) | |
| 3 | P를 삭제하고 commit | | `deleted_at` 기록 |
| 4 | | 재고를 4로 저장하고 commit | 전체 컬럼 UPDATE가 `deleted_at = null`로 덮어씀 → **삭제된 상품이 되살아남** |

- 순서를 바꾸면 삭제가 `stock = 5`로 덮어써 **재고가 되돌아간다.**
- 관리자의 가격 수정도 같은 문제를 만든다. 가격 수정 UPDATE가 `stock` 컬럼을 같이 써서 주문 차감이 사라진다.
- `@DynamicUpdate`로 바뀐 컬럼만 쓰게 해도 판단 문제는 남는다. T2는 스냅샷에서 "삭제 안 됨"을 보고 확정하므로 *삭제된 상품으로 주문이 확정*된다. "확정 시 삭제 여부를 다시 확인한다"는 요구는 **최신 상태를 읽을 때만** 의미가 있다.

**여기서 나온 기준**: 한 유스케이스만 잠그면 나머지가 우회로가 된다. 보호의 단위는 유스케이스가 아니라 **행**이고, 기준은 "모든 쓰기 경로가 최신 값 기준의 X 잠금 아래에서 계산한다"이다.

## 3. InnoDB REPEATABLE READ의 실제 동작

| SQL | 읽는 값 | 비고 |
|---|---|---|
| 일반 SELECT | 트랜잭션의 **스냅샷** (MVCC) | X 잠금에 막히지 않는다 |
| `SELECT … FOR UPDATE`·`FOR SHARE` | **최신 commit 값** | 잠금을 얻을 때까지 기다린다 |
| UPDATE | 최신 값을 읽고 X 잠금 | 조건도 최신 값으로 평가한다 |

- PostgreSQL의 RR은 같은 행의 동시 갱신을 직렬화 오류로 거절한다. **InnoDB의 RR은 갱신 유실을 감지하지 않는다.** 두 번째 UPDATE는 기다린 뒤 낡은 값으로 덮어쓴다.
- 그래서 RR이니까 안전하다고 생각하면 안 된다. 일반 SELECT와 잠금 읽기·UPDATE는 서로 다른 값을 본다.
- "처음 읽는 조회가 잠금 조회여야 한다"는 규칙의 근거는 두 겹이다.
  - **check-then-act (DB와 무관)**: 잠금 없이 읽은 값으로 판단하면 판단과 잠금 사이에 값이 바뀔 수 있다.
  - **영속성 컨텍스트 (JPA 추가 함정)**: 같은 트랜잭션에서 먼저 읽은 엔티티는 1차 캐시에 남아, 나중에 잠금 조회를 해도 낡은 객체가 돌려질 수 있다 (가설: 구현 때 확인). 컨텍스트는 트랜잭션마다 하나라 트랜잭션이 끝나면 사라진다.

**무엇이 보편적이고 무엇이 InnoDB RR만의 특이점인가.** `FOR UPDATE`가 기다린 뒤 최신 commit 값을 읽는 것은 READ COMMITTED를 쓰는 DB 대부분의 보편적 동작이다. InnoDB RR만의 특이점은 ① 한 트랜잭션에서 같은 행이 일반 SELECT와 `FOR UPDATE`로 서로 다른 값으로 보일 수 있다는 점, ② 잠금 읽기가 오류 없이 최신 값을 준다는 점이다. PostgreSQL RR에서는 ②가 `could not serialize access`로 rollback되어 재시도가 필요하다. 이 설계는 InnoDB RR의 특이점에 기대지 않으려고 정합성의 근거를 "① 처음 읽기가 잠금 읽기 ② 잠금을 얻은 뒤 읽은 값은 commit된 값" 두 가지로 좁혔다(처음 읽기를 지키면 두 값이 보이는 장면이 코드에 나타나지 않는다). 쓰기 경로만 READ COMMITTED로 명시하는 방안도 검토했으나, MySQL에서 흔한 패턴이 아니어서 RR 유지로 정리했다.

## 4. 우려 ①: 낙관적 잠금이면 트랜잭션이 길어지는가

정확히는 트랜잭션 하나가 길어지는 것이 아니라 **트랜잭션 수와 버려지는 작업이 늘어난다.**

- InnoDB에서 `UPDATE … WHERE id = ? AND version = ?`도 실행하는 순간 X 잠금을 잡는다. 앞 트랜잭션이 그 행을 쥐고 있으면 **commit까지 기다린 뒤** 0행으로 실패한다. "낙관적이라 기다리지 않는다"는 생각은 InnoDB에서 맞지 않는다.
- 재고 5에 주문 8건을 동시에 보내면 한 번에 한 건만 이기고 나머지는 처음부터 다시 시작한다. 최악에는 시도 횟수가 요청 수의 제곱에 가까워진다 (가설).
- 확정은 주문·상품 N개·사용자를 함께 바꾼다. 마지막 단계에서 충돌하면 앞의 재고 작업까지 rollback되고 전체를 다시 한다.
- 무관한 변경과 충돌한다. 브랜드 삭제나 관리자 가격 수정이 version을 올리면 진행 중인 확정이 재고와 상관없는 이유로 실패한다. 재시도 끝에 삭제를 보고 거절하는 것은 맞지만, 가격 수정 때문의 충돌은 업무상 의미 없는 충돌이다.
- 재시도는 Facade 트랜잭션 **밖**의 별도 bean에서 새 트랜잭션으로 해야 한다 (같은 객체 안에서 부르면 프록시를 거치지 않는다). 횟수·대기 한도를 넘긴 경우를 재고 부족과 섞지 않고 따로 집계해야 한다.

낙관적 잠금이 맞는 곳은 충돌이 드물고 사람의 생각 시간이 트랜잭션 사이에 끼는 경우다. 예를 들어 관리자가 수정 폼을 열어 두고 저장하는 경우다.

## 5. 우려 ②: 비관적 잠금이면 교착이 생기는가

교착은 두 트랜잭션이 각자 **둘 이상의 잠금을 서로 다른 순서로** 잡을 때만 생긴다. 그래서 유스케이스별 잠금 집합을 적어 보면 판단할 수 있다.

| 유스케이스 | 잠금 (순서대로) | 개수 |
|---|---|---|
| 주문 확정 | 주문 → 상품(id 오름차순) → 사용자 | 여러 개 |
| 브랜드 삭제 | 브랜드 → 그 브랜드의 상품(id 오름차순) | 여러 개 |
| 상품 등록 | 브랜드(공유) | 1 |
| 포인트 충전 | 사용자 | 1 |
| 관리자 재고 설정·상품 수정·삭제 | 상품 | 1 |
| 주문 생성·좋아요·고객 조회 | 없음 (MVCC) | 0 |

- 잠금을 여러 개 잡는 것은 **확정과 브랜드 삭제 둘뿐**이다. 전역 순서를 `주문 → 브랜드 → 상품(id 오름차순) → 사용자`로 정하면 대기 관계에 순환이 생기지 않는다. (순서는 순환을 막는 규칙일 뿐 처리 속도를 바꾸지 않는다. 주문을 앞에 둔 것은 확정이 주문을 읽어야 품목·상품을 알 수 있어 읽기 순서와 맞기 때문이다.)
- 말씀하신 "브랜드 삭제의 대량 업데이트"는 **그 브랜드의 상품 행만** 잠근다. 다른 브랜드 상품의 확정에는 영향이 없다.
- 브랜드 행이 문지기다. 삭제(X)와 상품 등록(S)이 모두 브랜드를 먼저 잡으므로 "삭제 후 미삭제 상품이 남는" 경쟁이 닫힌다.

그래도 남는 위험:

1. 상품 조회를 품목 순서대로 하나씩 잠그면 순서가 깨진다. `IN (…) ORDER BY id FOR UPDATE` **한 번**으로 잡아야 한다.
2. RR에서 보조 인덱스(`brand_id`) 범위 잠금은 next-key·갭 잠금을 잡는다. 이웃 브랜드에 상품을 넣는 요청이 잠깐 기다릴 수 있다 (가설: `data_locks`로 확인). 순환이 아니라 불필요한 대기다.
3. 새 경로가 순서를 어기면 교착이 생긴다. 순서를 규칙으로 문서에 남기는 이유다.
4. InnoDB는 교착을 즉시 감지해 한쪽을 rollback한다. 이를 품절·잔액 부족으로 바꾸지 않고 **기술 오류**로 집계한다. 경쟁 테스트의 "기술 오류 0"이 이 설계를 검증한다.

**진짜 비용은 교착보다 커넥션 점유다.** 잠금을 기다리는 요청도 커넥션을 쥔다. 한 상품에 요청이 몰리면 풀(10)이 바닥나 무관한 요청이 커넥션 획득 대기(3초)를 넘길 수 있다. 대응은 잠금 대기 한도를 짧게 두는 것인데, 방법은 아직 확인하지 않았다 (열린 항목: MySQL에는 밀리초 대기 구문이 없어 JPA hint가 적용되지 않을 수 있다).

## 6. 포인트: 충돌이 드물다면 무엇이 달라지는가

### 6-1. 처음의 직관

"동시 충돌이 드물면 낙관적 잠금도 되고, 비관적 잠금을 써도 비용이 없다." 둘 다 맞다. 충돌이 드물면 아무도 기다리지 않으므로 비관적 잠금의 비용도 거의 없다. 그래서 비용 대신 **구조**가 판단 기준이 된다.

- 확정은 이미 상품을 비관적으로 잡은 상태다. 그 뒤 사용자 `@Version` 충돌이 나면 *잡아 둔 상품 잠금과 재고 작업을 모두 버리고* 재시도해야 한다.
- 충전만 낙관적으로 재시도하는 절충안은 동작한다. 하지만 InnoDB에서 충전 UPDATE도 결국 행 잠금을 기다리므로 얻는 것이 없고 재시도 장치만 늘어난다.

### 6-2. 조건부 갱신을 다시 보다

처음에는 조건부 갱신을 "트랜잭션이 끝날 때까지 X 잠금이 유지되므로 잠금 시간에서 이득이 없다"고 한 줄로 기각했다. 이 판단은 성급했다. 다시 보니 조건부 갱신이 더 맞는 조건이 분명히 있다.

조건부 갱신이 맞는 네 조건:

1. 불변식이 **행 하나의 조건 하나**로 표현된다.
2. 영향 행이 0일 때 **실패 이유가 하나**다.
3. 갱신 뒤 엔티티 상태가 거의 필요 없다.
4. 경쟁이 잦아서 짧은 잠금 구간이 의미가 있다.

장점도 분명하다.

- "처음 읽을 때 잠가야 한다"는 규율이 필요 없다. 엔티티를 읽지 않으므로 낡은 스냅샷으로 판단할 틈이 없다.
- 필요한 컬럼만 바꾼다. 2장의 전체 컬럼 덮어쓰기 문제가 구조적으로 생기지 않는다.
- 왕복이 한 번이다.

섞어 쓸 수 있는가? 판단 기준을 "모든 쓰기가 최신 값 기준의 X 잠금 아래에서 계산해야 한다"로 고치면 답이 나온다.

| 같은 행을 쓰는 다른 경로 | 조건부 갱신과 함께 써도 되는가 |
|---|---|
| `FOR UPDATE`로 읽고 엔티티로 쓰기 | 안전하다. 둘 다 최신 값 기준이다 |
| 잠금 없이 읽고 전체 컬럼으로 쓰기 | **위험하다.** 조건부 갱신의 결과를 덮어쓴다 |
| `@Version` 낙관적 잠금 | 조건부 SQL도 `version = version + 1`을 직접 써야 한다 |

### 6-3. 유스케이스 대조

| 유스케이스 | ① 조건 하나 | ② 0행 원인 하나 | ③ 엔티티 불필요 | ④ 경쟁 잦음 | 판단 |
|---|---|---|---|---|---|
| 포인트 결제 | `balance >= ?` | 잔액 부족뿐 (사용자 존재는 필터가 보장, soft delete 없음) | 결제 후 잔액만 다시 읽음 | 낮음 | 조건에 맞음 |
| 포인트 충전 | 상한 조건 하나 | 범위 초과 하나 | 잔액만 다시 읽음 | 낮음 | 조건에 맞음 |
| 재고 차감 | `stock >= ? AND deleted_at IS NULL` | **삭제 / 부족 둘** | 오류 메시지에 품목 이름 필요 | **높음** | 어색함 |
| 주문 상태 | `status = 'DRAFT'` | 이미 확정 하나 | 결제 결과를 함께 써야 함 | 낮음 | 가능하나 이점 적음 |
| 브랜드 삭제·상품 등록 | — | — | — | — | 맞지 않음. 불변식이 행 하나의 값이 아니라 *행 집합의 구성*이다. 조건부 UPDATE는 이후의 INSERT를 막지 못한다 |

**재고 차감에서 ②가 깨지는 지점 (RR 함정)**

- 확정의 오류 계약은 "삭제된 상품을 모두 주문 당시 이름으로 먼저 알리고(`PRODUCT_UNAVAILABLE`), 그다음 재고 부족(`OUT_OF_STOCK`)"이다.
- 영향 행이 0이면 원인을 가리려고 다시 조회해야 한다. 그런데 RR의 일반 SELECT는 *트랜잭션 시작 시점의 스냅샷*을 본다. "삭제 안 됨, 재고 5"처럼 0행과 모순되는 값이 나올 수 있다.
- 올바르게 가리려면 결국 잠금 읽기가 필요하고, 그 순간 비관적 잠금과 같은 구조로 돌아온다.

### 6-4. 포인트 장단점 비교

| 관점 | 비관적 잠금 | 조건부 갱신 |
|---|---|---|
| 규칙의 위치 | `PointBalance`·`Money` 한 곳 | 잔액 판정이 SQL로 이동. 규칙이 두 곳이 되거나 `PointBalance.pay`가 쓰이지 않음 |
| 프로젝트 관례 | "규칙은 모델에" 유지 | 관례의 예외 → 정책 변경 |
| 규칙 확장 | 일일 한도, 이력, 만료를 자바 코드로 추가 | 조건이 복잡해지거나 결국 잠금 읽기로 돌아옴 |
| 경쟁 안전성의 근거 | 규율에 의존 (처음 읽기가 잠금 읽기) | 구조적으로 안전 |
| 다른 컬럼과의 간섭 | 전체 컬럼 UPDATE (지금은 잔액뿐이라 무해) | 잔액 컬럼만 변경 |
| JPA 함정 | 적음 | `@PreUpdate` 우회로 `updated_at` 직접 기록, 1차 캐시 낡음, `@Modifying(clearAutomatically)`가 앞서 읽은 `Order`를 분리해 `confirm`이 저장되지 않을 수 있음 (가설: 구현 때 확인) |
| 확정의 사용자 처리 | 엔티티 잠금 조회 필요 (`User` 이중 조회 유지) | 엔티티를 읽지 않아 이중 조회 제거 |
| 성능·잠금 시간 | 왕복 2회, 사용자를 맨 마지막에 잡음 | 왕복 1회. 잠금은 둘 다 commit까지 유지되어 차이가 거의 없음 |
| 교착 | 같음 (사용자 행을 맨 끝에 잡는 X 잠금 하나) | 같음 |
| 테스트 | 기존 `PointBalance` 단위 테스트가 그대로 유효 | 잔액 규칙을 DB 통합 테스트로만 확인 |
| 0행의 의미 | 해당 없음 (예외 종류로 원인이 분명) | "사용자는 존재하고 soft delete가 없다"는 전제가 있어야 원인이 하나 |

### 6-5. 결론

- 조건부 갱신이 이기는 것은 구조적 안전성과 이중 조회 제거인데, 둘 다 지금 `User`가 단순해서 현재 피해가 작다.
- 비관적 잠금이 이기는 것은 규칙의 응집, 관례 유지, 확장 용이성, JPA 함정 회피다. 성능 차이는 거의 없다.
- 그래서 **포인트는 비관적 잠금**으로 정했다. 비관적 잠금의 약점인 "규율"은 잠금 조회 전용 메서드(`getForUpdate`)와 경쟁 테스트로 메운다.
- 이 비교에서 처음에 빠졌던 것은 **프로젝트 관례(규칙은 모델에)를 비용으로 셈하는 일**이었다. 처음 권했던 조건부 갱신은 안전성만 보고 이 비용을 계산에 넣지 않았다.

**전체 결론**: 조건부 갱신에 *맞는 곳*(포인트)과 *경쟁이 몰리는 곳*(재고)이 겹치지 않는다. 앞의 곳은 경쟁이 드물어 이득이 작고, 뒤의 곳은 실패 이유가 둘이라 조건부 갱신이 어색하다.

결과가 뒤집히는 조건(재검토 조건):

- 재고 차감만 하는 짧은 트랜잭션(선착순 API)이 생기는 경우
- 확정 오류 계약을 "구매 불가" 하나로 합치는 경우
- 포인트 규칙이 계속 단순하고 경쟁이 잦아지는 경우

## 7. 기각한 대안 요약

| 대안 | 기각 이유 |
|---|---|
| 낙관적 잠금 (재고·주문) | 요청이 몰리는 곳에서 재시도 폭증, 무관한 변경과 거짓 충돌, 확정 마지막 단계 충돌 시 앞 작업 낭비, InnoDB에서 version UPDATE도 행 잠금을 기다림 |
| 재고의 조건부 갱신 | 0행의 원인이 둘이고 원인을 가리는 재조회는 갱신과 원자적이지 않다(InnoDB RR의 일반 SELECT는 스냅샷이라 모순된 값까지 나온다). 구분에 결국 잠금 읽기가 필요 |
| 포인트의 조건부 갱신 | 규칙이 SQL로 분산되고 관례가 바뀜, 성능 이득 없음 |
| SERIALIZABLE | 직렬화 실패(교착·직렬화 오류)가 일상화되고 재시도가 필요해 "기술 오류 0" 불가. InnoDB에서는 일반 SELECT가 공유 잠금이 되어 S→X 승격 교착으로 나타남 (가설) |
| READ COMMITTED 전역 변경 | 서비스 전체 정책 변경이고 `modules` 공유 설정에 영향. 읽고 판단한 뒤 쓰는 사이의 경쟁은 이것만으로 해결되지 않아 잠금이 여전히 필요 |
| 쓰기 경로만 READ COMMITTED 명시 | MySQL에서 흔한 패턴이 아니고 트랜잭션마다 전환 비용. 읽는 쪽이 "왜 여기만 RC인가"를 따로 이해해야 함 |
| 사용자 `@Version` + 충전만 낙관적 재시도 | InnoDB에서 얻는 것이 없고 재시도 장치만 늘어남 |
| 전역 `synchronized` | 프로세스가 다르면 보호되지 않고, 서로 다른 상품까지 기다리게 함 |

## 8. 아직 확인하지 않은 것

- 잠금 대기 한도를 짧게 두는 방법 (JPA hint, 세션 변수, 커넥션 설정). MySQL에는 밀리초 대기 구문이 없어 hint가 적용되지 않을 수 있다.
- Hibernate가 MySQL 8.0에서 `PESSIMISTIC_READ`를 `for share`로 만드는지.
- `IN … ORDER BY id FOR UPDATE`와 `WHERE brand_id = ? FOR UPDATE`의 실제 잠금 범위(`performance_schema.data_locks`).
- 갭 잠금 때문에 이웃 브랜드의 상품 등록이 얼마나 기다리는지.
- 낙관적 잠금에서 재시도가 몇 배 늘어나는지 (이번 과제는 비교 실험을 하지 않는다).
- 커넥션 풀 고갈이 실제로 어느 동시성부터 보이는지.

## 9. 칼럼으로 풀 때 쓸 수 있는 흐름

1. **상황**: 재고 5에 주문 8건. 잠금 없이 읽고 쓰면 성공 2 / 재고 4가 나오는 대조군 하나.
2. **반전**: 재고만 잠그면 끝일 줄 알았는데, 전체 컬럼 UPDATE가 삭제 표시와 재고를 서로 덮어쓰는 표 (2장).
3. **개념**: 원자성(한 문장 대 유스케이스), 격리(스냅샷 읽기 대 잠금 읽기), 잠금 순서와 교착 (3·5장).
4. **판단**: 유스케이스마다 잠금 집합을 적어 교착 가능성을 따진 표, 낙관적 잠금이 InnoDB에서 기다리는 이유 (4·5장).
5. **수정한 판단**: 조건부 갱신을 성급히 기각했다가 적합 조건 네 개로 다시 따진 과정, 비용에 프로젝트 관례를 넣고 비관적 잠금으로 돌아온 이유 (6장).
6. **한계**: 8장의 미확인 항목과 재검토 조건.
