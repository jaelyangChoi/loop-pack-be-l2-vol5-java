## 설계 단계 개념

**버드뷰(Bird's-eye view)**
상세 클래스도를 그리기 전에, 누가(고객/관리자) 무엇을 요청하고 어떤 시스템(API 서버, DB)이 처리하는지
전체 그림을 먼저 보는 것입니다. 이번 과제의 설계 문서 첫 항목이 이 그림이며, 세부 구현이 맡을 역할을
찾기 위한 출발점으로 요구됩니다.

**도메인 모델링**
업무의 개념과 규칙을 객체의 상태·행동·관계로 표현하는 설계 작업입니다. 테이블/클래스 이름을 나열하는
것과는 다릅니다. 이번 과제에서는 `Brand–Product`, `User–Like–Product`, `Order–OrderItem`, 사용자의 포인트
잔액 같은 관계를 이 방식으로 표현해야 합니다.

**ADR (Architecture Decision Record)**
중요한 설계 선택의 상황·대안·선택·비용·재검토 조건을 남기는 짧은 기록입니다. 설계 문서에서 "왜 이렇게
정했는지"를 설명할 때 쓰는 형식으로 원문에 언급됩니다. `docs/week1/order-discount-contract.md`의
"결정 1/2/3" 절이 비슷한 성격의 기록입니다.

## 객체지향 개념

**캡슐화**
관련 상태와 그 상태를 지키는 규칙을 한 객체 안에 모으고, 외부에는 의미 있는 행동만 공개하는 것입니다.
`private` 필드에 setter를 붙이는 것만으로는 충분하지 않고, 공개된 생성자·메서드로도 유효하지 않은 상태를
만들 수 없어야 합니다. 재고 차감, 포인트 충전/결제, 주문 확정 같은 과제 규칙이 이 원칙의 적용 대상입니다.

**Tell, Don't Ask**
호출자가 객체의 내부 값을 꺼내 규칙을 재조립하지 않고, 그 상태를 책임지는 객체에게 필요한 행동을
요청하는 스타일입니다. 조회용 getter는 허용되지만, getter+setter 조합으로 업무 규칙이 여러 호출자에
흩어지는 것이 문제라고 원문은 구분합니다.

**응집도 / 결합도 / 단일 책임 원칙(SRP)**
- 응집도: 함께 바뀌는 상태와 행동이 한 곳에 모여 있는지.
- 결합도: 한 부분의 변경이 다른 부분까지 번지는 정도.
- SRP: 서로 다른 변경 이유를 한 클래스가 같이 맡고 있지 않은지.
세 개념은 "클래스를 몇 개로 나눌지"보다 "무엇이 함께 바뀌어야 하는지"를 판단하는 기준으로 쓰입니다.

**Entity / Value Object / Domain Service / Application Service**
- Entity: 식별자와 생명주기가 중요한 객체(예: `Product`, `Order`).
- Value Object(VO): 값 자체의 의미·동등성이 중요한 객체(예: 금액을 표현하는 `Money`).
- Domain Service: 한 Entity에 자연스럽게 속하지 않는 업무 판단(예: 여러 상품의 재고·삭제 여부를 함께 보는 판단).
- Application Service(Facade): 유스케이스의 순서와 객체 협력을 조율하는 역할.
이번 과제에서 재고 차감, 포인트 잔액, 좋아요 관계, 주문 상태 같은 규칙을 어느 역할에 둘지 구분하는 데
쓰이는 분류입니다.

## 검증 방법론

**TDD (Test-Driven Development)와 Red → Green → Refactor**
기대 동작을 테스트로 먼저 표현하고, 실패(Red) → 최소 구현으로 통과(Green) → 구조 개선(Refactor)을
반복하는 개발 방식입니다. 이번 과제는 대표 도메인 규칙 하나(예: 재고 차감)에 이 절차를 직접 적용하라고
요구합니다. "정상 사례 없이 거절 사례만 있으면 모든 요청을 거절하는 구현도 테스트를 통과할 수 있다"는
점이 정상/오류 사례를 함께 두어야 하는 이유로 설명됩니다.

**lint / ArchUnit / 동작 테스트의 역할 구분**
- lint(Checkstyle/ktlint): 정한 스타일·정적 규칙을 확인. 업무 규칙의 옳고 그름은 판단하지 못함.
- ArchUnit: 컴파일된 클래스의 패키지·타입 의존 방향을 검사하는 표준 라이브러리. "런타임에 호출되는가"가
  아니라 "소스 코드가 어떤 타입에 의존하는가"를 검사함.
- 동작 테스트(단위/통합/HTTP): 특정 입력의 기대 결과를 확인. 작성하지 않은 경우는 검증하지 못함.
세 도구가 서로 다른 것을 검사하므로 하나로 나머지를 대체할 수 없다는 점이 이번 과제의 전제입니다.

## 구조 개념

**레이어드 아키텍처와 패키지/계층/모듈의 구분**
패키지(이름·위치를 묶는 단위), 계층(HTTP 처리·유스케이스·업무 규칙·저장 구현 같은 책임의 종류), 모듈
(빌드·의존 설정의 경계)은 서로 다른 개념입니다. 이 저장소의 `interfaces.api / application / domain /
infrastructure` 4계층 구조가 이번 과제가 전제하는 layer-first 방식입니다.

**DIP (Dependency Inversion Principle)**
높은 수준의 정책(도메인/애플리케이션 로직)이 저장 기술 같은 세부 구현에 직접 의존하지 않고, 양쪽이
추상화(인터페이스)에 의존하게 하는 원칙입니다. "런타임 호출 방향과 소스의 타입 의존 방향은 다르다"는
문장이 핵심으로, `domain`에 `Repository` 인터페이스만 두고 `infrastructure`가 이를 구현하는 이 저장소의
기존 패턴이 그 예시입니다.

**Layer-first vs Feature-first**
계층별로 폴더를 나누는 방식(layer-first)과 기능별로 폴더를 나누는 방식(feature-first)의 비교입니다.
이번 과제는 layer-first(현재 저장소 구조)를 전제로 예시를 제공하지만, 어떤 구조든 "무엇에 의존해도
되는지"를 설명할 수 있어야 한다는 점을 원문이 강조합니다.

**Hard delete vs Soft delete**
- Hard delete(물리 삭제): 행 자체를 제거. 외래 키·연쇄 삭제 설정이 영향 범위를 결정.
- Soft delete(논리 삭제): 행은 남기고 `deletedAt` 같은 값으로 삭제 상태만 표시. 조회 시 "존재"와
  "사용 가능"을 별도로 판단해야 함.
이번 과제의 브랜드/상품 삭제 조건(삭제되지 않은 상품이 있으면 브랜드 삭제 거절 등)을 구현할 때 두 방식
중 하나를 선택하고 이유를 남겨야 하는 지점과 연결됩니다.

## AI 협업 관련 개념

**AI와의 설계 검토 절차**
초안을 만든 뒤 AI에게 책임 중복·의존 취약점을 질문하고, AI가 제시한 대안들을 반례("이 값이 바뀌면
어떤 객체까지 바뀌는가?")로 검증한 뒤 선택하는 절차입니다. 이번 과제는 이 절차를 설계 문서 작성
단계와 작은 기능 구현 단계 양쪽에 적용하도록 요구합니다.

**작업 지시 명세(기능/정책/허용 변경/검증/금지)**
AI에게 작은 기능을 요청할 때 기능 범위, 지켜야 할 정책, 허용된 변경 범위, 검증 방법, 금지 사항을 함께
전달하는 방식입니다. 원문은 이 형식을 명시적 예시로 제공하며, `CLAUDE.md`/`AGENTS.md`에 팀의 AI 작업
규칙으로 반영하라고 안내합니다.
