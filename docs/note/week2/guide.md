## 1. 내가 해야 할 일

### 1-1. 설계 문서 작성

하나의 설계 문서에 아래 네 가지를 담아야 합니다 (원문 표 그대로).

| 표현할 것 | 담을 내용 |
|---|---|
| 버드뷰 | 고객·관리자, API 서버, DB와 요청 방향 |
| 구조와 의존 | interfaces / application / domain / infrastructure의 역할과 허용 방향 |
| 도메인 관계 | Brand–Product, User–Like–Product, Order–OrderItem과 재고·포인트의 책임 |
| 대표 흐름 | 관리자 변경→고객 조회, 좋아요 등록·취소, 포인트 충전→주문 확정 중 선택한 흐름 |

- 기본 API의 method/path/입력/성공/대표 오류, 주요 규칙의 기대값도 같은 문서에 함께 적으라고 되어 있습니다.
- **위치 매핑**: 이 산출물 자체는 제품 코드가 아니라 `docs/` 하위 설계 문서입니다. 1주차의
  `docs/week1/order-discount-contract.md`가 같은 성격의 산출물 예시입니다.
- 원문은 "AI와 설계 다듬기" 단계를 별도로 언급합니다 — 초안을 만든 뒤 책임 중복·의존을 AI에게 질문하고,
  제시된 대안을 반례로 검증하라는 절차입니다. 어떤 대안을 고를지는 원문에 없고, 그건 본인이 정할 부분입니다.

`infrastructure`에 의존하지 않음)과 동일합니다. 즉 이번 과제는 그 원칙을 **테스트로 강제**하는 작업입니다.

### 1-3. 기본 기능 구현 (TDD + AI 협업)

원문은 "대표 도메인 규칙 하나를 골라 TDD(Red → Green → Refactor)를 적용"한 뒤, 나머지는 AI와 작은 기능
단위로 구현하라고 되어 있습니다. 어떤 규칙을 대표로 고를지, 어떻게 구현할지는 본인 판단입니다.

구현 대상 API는 원문 표를 그대로 옮겼습니다. **위치 매핑**: 원문이 예시로 든 패키지 구조
(`interfaces/api/product → application/product → domain/product`, `infrastructure/product → domain/product`)는
CLAUDE.md의 4계층 구조와 동일한 패턴이며, 현재 `commerce-api`의 `example` 도메인에만 실제 구현되어 있는
템플릿을 새 도메인(`product`, `brand`, `like`, `point`, `order`)에 이식하는 작업으로 보입니다(레이어 이름은
원문에 명시, 구체적 파일 배치는 추정).

**🏷 상품·브랜드·좋아요**

| 기능 | API | 핵심 조건 |
|---|---|---|
| 브랜드 상세 | `GET /api/v1/brands/{brandId}` | 존재하며 삭제되지 않은 브랜드 조회 |
| 상품 목록·상세 | `GET /api/v1/products`, `GET /api/v1/products/{productId}` | 브랜드 정보·좋아요 수 포함 |
| 상품 목록 조건 | 브랜드 필터·페이지 조회, `latest`·`price_asc`·`likes_desc` 정렬 | 동률의 보조 정렬 기준과 잘못된 입력 처리 |
| 좋아요 등록·취소 | `POST/DELETE /api/v1/products/{productId}/likes` | 사용자–상품 관계로 저장, 중복 관계 방지 |
| 내 좋아요 목록 | `GET /api/v1/users/{userId}/likes` | 자신의 관계만 조회·취소, 상품의 좋아요 수에 반영 |

- 좋아요 수는 관계에서 조회(원문 명시). 삭제된 상품은 새 좋아요·내 목록에서 제외하되, 남아 있는 자신의
  좋아요 관계는 취소 가능해야 합니다.
- 없거나 삭제된 대상의 고객 상세 조회는 "없는 대상 오류"로 처리합니다.

**💰 포인트·주문**

| 기능 | API | 핵심 조건 |
|---|---|---|
| 내 포인트 충전 | `POST /api/v1/points/charge` | `amount`를 잔액에 더해 DB 저장, 충전 후 잔액 반환 |
| 내 잔액 조회 | `GET /api/v1/points` | 요청자로 식별한 사용자의 저장된 잔액 조회 |
| 주문 생성 | `POST /api/v1/orders` | 여러 품목·수량·단가·합계를 DRAFT로 저장, 생성 시 차감 없음 |
| 주문 확정 | `POST /api/v1/orders/{orderId}/confirm` | 본인의 DRAFT 주문 확정, 재고·포인트 차감, 결제액·결과 저장, CONFIRMED로 변경 |
| 내 주문 목록·상세 | `GET /api/v1/orders`, `GET /api/v1/orders/{orderId}` | 내 주문의 품목·수량·금액·상태·결제액 조회 |

- 1포인트 = 1원(원문 명시). 충전액은 양의 정수, 누락·잘못된 타입·표현 범위 초과는 거절.
- 잔액 0원은 허용. 충전 입력 오류 시 기존 값 유지.
- DRAFT(확정 전) / CONFIRMED(결제 완료) 두 상태. **생성 시 차감하지 않고 확정 시 차감**(원문 명시, 순서 뒤바뀌지 않도록 주의).
- 중복 상품 품목은 "합산하거나 거절" 중 택1 — 원문이 정책을 확정하지 않았으므로 본인이 정하고, 어느 쪽이든
  총수량 기준으로 재고를 확인해야 합니다.

**🛠 관리자**

| 기능 | API | 핵심 조건 |
|---|---|---|
| 브랜드 전체 CRUD | `GET/POST /api-admin/v1/brands`, `GET/PUT/DELETE /api-admin/v1/brands/{brandId}` | 유효한 브랜드 정보 저장·조회, 연결된 상품의 삭제 조건 확인 |
| 상품 전체 CRUD | `GET/POST /api-admin/v1/products`, `GET/PUT/DELETE /api-admin/v1/products/{productId}` | 삭제 안 된 브랜드 참조, 이름·가격 범위 검증, 수정 시 브랜드 유지 |
| 상품 재고 변경 | `PUT /api-admin/v1/products/{productId}/stock` | 0 이상인 최종 수량 설정 |
| 주문 목록·상세 | `GET /api-admin/v1/orders`, `GET /api-admin/v1/orders/{orderId}` | 구매자별 주문의 품목·상태·금액·결제 결과 조회 |

**기본 삭제 조건(원문 명시)**

- 삭제되지 않은 상품이 연결된 브랜드의 삭제는 거절(재고 0인 상품도 포함).
- 삭제된 브랜드·상품은 고객 조회·새 주문에서 제외하며, 수정·재고 변경 대상으로도 사용하지 않음.
- 물리 삭제/논리 삭제 중 무엇을 쓸지는 원문이 정하지 않았고, 선택 후 이유를 설계 문서에 적으라고만 되어 있습니다.

**위치 매핑**: 관리자 접근 통제는 원문이 `com.loopers.config`에 `AdminBoundaryConfig`(Spring Security
`SecurityFilterChain`)를 추가하도록 코드 예시를 직접 제공합니다. 이는 `apps/commerce-api`의 `main` 소스,
즉 인프라 설정에 가까운 위치입니다. `spring-boot-starter-security`, `spring-security-test` 의존성 추가가
필요하다고 원문에 명시되어 있습니다.

### 1-4. 실행·제출

- 고객 요청에는 1주차에 정한 로컬 실습용 사용자 식별을 재사용합니다(원문 명시). 식별 누락·없는 사용자는
  거절하고, 본인의 좋아요·포인트·주문만 다루는지 확인해야 합니다.
- 관리자 API는 MockMvc + `SecurityMockMvcRequestPostProcessors.user(...)`/`csrf()`로 관리자·일반·미식별
  요청 세 가지를 각각 검증(원문이 예시 코드 제공).
- 최종 검사 명령(원문 그대로):
  - Java: `./gradlew :apps:commerce-api:check` (Checkstyle 연결 후)
  - 관련 테스트만: `./gradlew :apps:commerce-api:test --tests '*Stock*Test'`, `--tests '*ArchitectureTest'`
- 제출물: 구현·테스트·검사 설정, 설계 문서, PR 설명, 기술 글. PR에는 대표 TDD 사례 변화, 설계에서 바뀐
  판단, 실행한 검사를 짧게 적으라고 되어 있습니다.

이번 주 이해가 달라진 주제 하나를 자신의 코드와 함께 설명하는 별도 산출물입니다(저장소 Markdown·Issue·

## 2. 어떤 의도의 과제인지

발제 설명 문서의 Summary/Learning 섹션에서 읽히는 의도입니다.

- 원문이 명시한 다섯 개 축: 설계(버드뷰·도메인 관계·패키지 의존·대표 유스케이스), 객체지향(캡슐화, Tell
  Don't Ask, 응집도·결합도, SRP), TDD(Red→Green→Refactor), AI 협업(계약·기대값 안에서 작은 기능을
  구현·리팩터링), 기본 기능(상품·브랜드·좋아요, 포인트, 주문, 관리자 CRUD).

  테스트로, 의존 방향/스타일은 lint·ArchUnit으로 각각 확인하라는 것이 이 주차가 훈련시키려는 핵심
  역량으로 읽힙니다.
- AI 협업 관련해서는 "AI와 협업할 때도 제품 정책과 정답의 책임은 사람에게 있다. 구현과 그 구현을 평가할
  기대값을 동시에 맡기지 않는다"는 문장이 명시적으로 강조되어 있습니다.

## 3. 중요 포인트

### 확인된 사실(원문에 명시된 제약)

- 생성 시 차감하지 않고, 확정 시 차감한다(주문 생성 vs 확정의 순서).
- 좋아요는 사용자–상품 관계로 저장하고, 좋아요 수는 그 관계에서 조회한다(별도 카운터 관리는 원문이
  "가능하지만 관계-카운터 일치 책임이 추가된다"고만 언급하고 선택을 강제하지 않음).
- 삭제되지 않은 상품이 있는 브랜드의 삭제는 거절하며, 재고 0인 상품도 이 조건에 포함된다.
- 삭제된 브랜드·상품은 고객 조회·새 주문·수정·재고 변경 대상에서 제외한다.
- 관리자 접근 통제는 **로컬 실습용 모의 인증**이며, 원문이 "고정 관리자 헤더는 운영 인증 수단으로 사용하지
  않는다", "공개 배포와 실제 비밀정보·개인정보 사용은 하지 않는다"고 명시적으로 경고하고 있습니다.
- ArchUnit은 "실행 중 호출 방향"이 아니라 "컴파일된 클래스의 패키지·타입 의존"을 검사하는 도구라고 원문이
  구분합니다. 검사가 실패했을 때 검사 대상을 지우거나 실패를 무시하는 것은 해결 방법이 아니라고 별도
  경고(callout)로 명시되어 있습니다.

### 원문이 확정하지 않고 남겨둔 것 (직접 정해야 하는 부분)

- 상품 목록 정렬의 동률 처리 시 보조 정렬 기준.
- 중복 상품 품목을 합산할지 거절할지.
- 좋아요 수를 관계에서 매번 계산할지 별도 카운터로 관리할지.
- 물리 삭제/논리 삭제 중 어떤 방식을 쓸지(원문은 "선택하고 이유를 설계에 적으라"고만 함).
- 대표 TDD 대상으로 어떤 규칙을 고를지(원문은 "재고 5개→6개 차감 거절" 하나만 예시로 듦).

### 이전 주(1주차) 산출물과의 연결 — 확인되지 않은 부분

- `docs/week1/order-discount-contract.md`는 "주문 확정 전 쿠폰 적용, 확정된 할인 금액은 이후 바뀌지 않는다"는
  **쿠폰 할인** 시나리오를 다루며, 문서 본문에 "W2에서 이 문서를 테스트와 코드로 옮긴다"고 적혀 있습니다.
- 그런데 이번에 fetch한 2주차 실습 과제/발제 설명 두 문서에는 쿠폰 관련 내용이 전혀 없고, 상품·브랜드·좋아요·
  포인트·주문(쿠폰 없는 단순 결제) 기본 기능만 다룹니다.
- 즉 **1주차 문서가 예고한 "W2 작업"과 실제로 fetch한 2주차 발제 내용이 서로 다른 시나리오를 가리키는 것으로
  보입니다.** 이 불일치는 노션 문서만으로는 해소되지 않으므로, 실제로 이번 주 과제 범위에 쿠폰 기능이
  포함되는지는 확인이 필요한 항목으로 남겨둡니다. (두 문서 다 텍스트는 정상적으로 읽혔고, 이미지/첨부
  누락으로 인한 "확인 불가"는 아닙니다.)
- 다만 4계층 아키텍처, TDD, ArchUnit 같은 방법론적 연속성은 1주차 문서에도 이미 전제되어 있어(예:
  `interfaces.api`/`application`/`domain`/`infrastructure` 구분, Facade 오케스트레이션) 이 부분은 그대로
  이어지는 것으로 보입니다.

### 노션에서 확인하지 못한 항목

- 발제 설명 문서 하단 References의 두 링크("3기 · Domain Modeling & Development", "공통 이커머스 시나리오")는
  별도 페이지라 이번에 fetch·확인하지 않았습니다.
- 두 문서 모두 이미지·첨부 전용 블록(텍스트 없는 블록)은 발견되지 않았습니다.
