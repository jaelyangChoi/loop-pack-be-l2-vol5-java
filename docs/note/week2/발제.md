## 🧭 서비스의 버드뷰와 도메인 모델링

> **버드뷰**는 상세 클래스도를 그리기 전에, 누가 무엇을 요청하고 어느 시스템이 처리하는지 파악하는 전체 그림입니다.
>

고객과 관리자, API 서버, DB를 먼저 연결해 보면 세부 구현이 맡아야 할 역할을 찾기 쉽습니다. 하나의 서버와 DB로 설명할 수 있다면 그 구조에서 시작하고, 각 구성 요소가 필요한 이유를 확인합니다.

```
고객 ── 상품·브랜드 조회 / 좋아요 / 포인트 / 주문 ─┐
                                                 ├─ commerce-api ─→ DB
관리자 ── 브랜드·상품 CRUD / 재고 변경 / 주문 조회 ─┘   고객·관리자 API 구분
```

고객과 관리자가 같은 상품을 다룬다고 **같은 입력과 권한**을 갖는 것은 아닙니다. 고객의 가격 조회와 관리자의 가격 변경은 서로 다른 계약입니다.

API의 입력·성공 결과·대표 오류를 함께 보면 책임이 구체화됩니다. `상품 수정`이라는 이름만으로는 가격만 바꾸는지, 브랜드까지 바꾸는지 알 수 없습니다. **변경할 수 있는 것과 지켜야 할 조건**이 모델의 행동과 테스트를 결정합니다.

### 🔗 도메인 관계와 업무 규칙

> **도메인 모델링**은 업무의 개념과 규칙을 객체의 상태·행동·관계로 표현하는 설계입니다. 테이블이나 클래스 이름을 나열하는 일에 그치지 않습니다.
>

과제의 브랜드·상품을 `Brand`·`Product`, 좋아요 관계를 `Like`, 주문과 각 품목을 `Order`·`OrderItem`으로 표현해 봅시다. `User`는 이 기능을 사용하는 실습용 고객입니다.

```
Brand 1 ── N Product
User  1 ── N Like N ── 1 Product
User  1 ── N Order 1 ── N OrderItem ── 상품 식별자·수량·단가
User  1 ── 포인트 잔액
Order ── 품목 금액 합계 / 포인트 결제액·결제 결과
```

이 그림의 선은 **업무 관계**를 설명합니다. JPA는 객체를 DB의 행과 연결하는 저장 도구이며, 이 선을 모두 서로 참조하는 객체 관계로 구현할 필요는 없습니다. 식별자만 보관할지, 객체로 참조할지는 실제 조회와 변경에 필요한 정보를 보고 정합니다.

| 질문 | 모델에 필요한 표현 |
| --- | --- |
| 누가 이 상품에 좋아요를 눌렀는가? | 사용자와 상품의 관계인 `Like` |
| 여러 상품의 주문 금액은 어떻게 구하는가? | 품목별 수량·단가와 품목 금액의 합계 |
| 재고 5개에서 6개를 차감해도 되는가? | 재고의 유효성을 지키는 행동 |
| 잔액 0원과 충전 요청 0원은 같은 조건인가? | 잔액의 유효 범위와 충전 행동의 입력 조건 |
| 삭제되지 않은 상품이 남은 브랜드를 삭제해도 되는가? | 브랜드와 상품 관계를 확인하는 삭제 조건 |
| 이 주문을 누가 조회할 수 있는가? | 주문 소유자와 요청자의 관계 |

“재고는 음수가 되지 않는다”와 “상품 목록에 브랜드명을 보여 준다”는 같은 종류의 요구가 아닙니다.

- **상태의 규칙**: 재고가 유효한 범위를 벗어나지 않아야 합니다.
- **조회 결과의 구성**: 상품과 브랜드 정보를 조합해 필요한 응답을 만듭니다.

클래스 수를 늘리기 전에 이 차이를 구분해야, 규칙을 지키는 객체와 결과를 조합하는 책임을 나눌 수 있습니다.

### 🧭 설계 판단과 변경 이유

설계 그림과 계약은 구현에서 내린 판단을 설명해야 합니다. 구현 중 더 나은 판단을 했다면 그림도 바뀔 수 있습니다. 처음 그린 그림을 유지하려고 잘못된 코드를 남기는 것은 설계의 목적이 아닙니다.

**ADR(Architecture Decision Record)**은 중요한 선택의 이유를 남기는 짧은 기록입니다. 상황, 대안, 선택과 비용, 다시 검토할 조건을 적으면 변경 이유를 설명할 수 있습니다. 문서의 양보다 **어떤 판단을 왜 했는지**가 중요합니다.

## 🧱 객체지향과 캡슐화

다음 코드는 호출자가 상품의 재고를 꺼내고, 조건을 검사하고, 새 값을 계산해 넣습니다.

```java
if (quantity > 0 && product.getStock() >= quantity) {
    product.setStock(product.getStock() - quantity);
}
```

주문 확정과 관리자 재고 변경이 같은 값을 바꾸면 각 호출자가 검사를 반복합니다. 한 곳에서 검사를 빠뜨리면 유효하지 않은 상태가 만들어질 수도 있습니다.

> **캡슐화**는 관련 상태와 그 상태를 지키는 규칙을 모으고, 외부에는 의미 있는 행동을 공개하는 것입니다.
>

```java
stock.decrease(quantity);
```

이제 호출자는 “재고를 차감해 달라”는 의도를 전달합니다. 수량이 양수인지, 보유 재고가 충분한지는 그 상태를 가진 객체가 판단합니다.

필드에 `private`을 붙여도 setter로 아무 값이나 넣을 수 있다면 충분하지 않습니다. **공개된 생성자와 행동을 사용해도 객체가 자신의 유효한 상태를 지켜야 합니다.** `decrease(-1)`이나 보유량을 넘는 차감을 객체가 거절해야 하는 이유입니다.

### 🗣️ Tell, Don’t Ask

> 내부 값을 받아 규칙을 재조립하기보다, **그 상태를 책임지는 객체에 필요한 행동을 요청합니다.**
>

조회 화면에 필요한 재고를 읽는 getter는 괜찮습니다. 문제는 getter와 setter를 조합한 **업무 규칙이 여러 호출자에게 흩어지는 것**입니다.

- `Stock.decrease(quantity)`: 유효한 수량과 충분한 재고를 확인하고 차감합니다.
- `PointBalance.charge(amount)`와 `pay(amount)`: 충전의 양수 조건과 잔액·차감액의 관계를 각각 지킵니다.
- `Order.confirm(...)`: 주문 상태와 금액 관계를 확인하고 확정합니다.

객체가 HTTP 상태 코드나 DB 조회까지 알아야 한다는 뜻은 아닙니다. **자신의 규칙을 지키는 것**과 **모든 일을 혼자 수행하는 것**은 다릅니다.

### 🧩 응집도·결합도·단일 책임 원칙

| 개념 | 살펴볼 질문 | 예 |
| --- | --- | --- |
| **응집도** | 함께 바뀌는 상태와 행동이 모여 있는가? | 재고 유효성 검사와 차감이 같은 책임에 있음 |
| **결합도** | 한 부분의 변경이 어디까지 번지는가? | HTTP DTO 변경 때문에 재고 모델까지 바뀜 |
| **단일 책임 원칙(SRP)** | 서로 다른 변경 이유를 한 클래스가 맡고 있지 않은가? | 주문 규칙과 JSON 응답 형식을 분리함 |

클래스 수가 많다고 좋은 설계는 아닙니다. 같은 계산을 여러 서비스로 흩으면 협력만 복잡해질 수 있습니다. 반대로 규칙 하나를 바꿀 때 컨트롤러 세 곳을 고친다면, 한 책임이 흩어진 것은 아닌지 살펴봅니다.

## 📦 Entity, Value Object, Service

객체를 구분할 때는 이름보다 **무엇으로 동일성을 판단하는지**, **어떤 상태와 판단을 책임지는지**를 봅니다.

| 역할 | 구분 기준 | 예 |
| --- | --- | --- |
| **Entity** | 식별자와 이어지는 생명주기가 중요함 | 가격이 바뀌어도 같은 상품인 `Product`, 상태가 바뀌는 `Order` |
| **Value Object** | 값의 의미와 동등성이 중요함 | `Money`, 상품 단가·포인트 결제액 |
| **도메인 서비스** | 한 Entity에 자연스럽게 속하지 않는 업무 판단 | 여러 상품의 삭제 여부·재고를 함께 살펴 주문 가능 여부 판단 |
| **애플리케이션 서비스** | 유스케이스의 순서와 객체 협력을 조율함 | 모델 조회 → 행동 호출 → 저장 → 결과 구성 |
| **컨트롤러** | 외부 입력과 응답을 변환함 | 요청 파싱, 식별 입력 전달, 오류의 HTTP 매핑 |

상품의 이름과 가격이 바뀌어도 식별자가 같다면 같은 상품을 수정한 것입니다. 반면 금액이나 이름 값은 값 자체로 비교합니다. **식별자의 연속성**과 **값의 유효성**을 구분하는 출발점입니다.

공백뿐인 상품 이름은 모델의 규칙으로 거절할 수 있습니다. 반면 브랜드의 존재는 다른 객체를 조회해야 합니다. 자기 상태의 검사와 유스케이스의 협력을 구분하면 각 책임을 어디에 둘지 판단할 수 있습니다.

### 👍 좋아요 도메인: 수치와 관계

`likeCount`만 저장하면 좋아요 수는 알지만 **누가 눌렀는지**는 모릅니다. 같은 사용자가 다시 눌렀을 때 중복을 구분할 수 없고, 자신의 좋아요만 취소하기도 어렵습니다.

```kotlin
class Like(
    val userId: Long,
    val productId: Long,
    val likedAt: Instant,
)
```

좋아요를 사용자–상품의 관계로 저장하면 등록·취소의 의미가 분명해집니다.

- 관계가 없을 때만 등록합니다.
- 자신의 관계가 있을 때만 제거합니다.
- 같은 사용자–상품 관계는 하나만 저장하고, 좋아요 수를 0 이상으로 유지합니다.

좋아요 수는 관계에서 조회할 수 있습니다. 별도 카운터를 두는 방법도 있지만, 그때는 **관계와 카운터를 일치시키는 책임**이 추가됩니다. 관계에서 개수를 조회하는 기본안과 별도 카운터를 관리하는 방식의 비용이 다른 이유입니다.

### 💎 Value Object: 금액의 의미와 유효성

```java
record Money(long amount) {
    Money {
        if (amount < 0) {
            throw new IllegalArgumentException("금액은 음수일 수 없습니다.");
        }
    }

    Money minus(Money other) {
        if (other.amount > amount) {
            throw new IllegalArgumentException("차감액이 원금을 넘습니다.");
        }
        return new Money(amount - other.amount);
    }
}
```

정수 원화 금액을 가정한 예입니다. 연산은 기존 값을 바꾸지 않고 **새 값을 반환**합니다. 음수인 금액을 만들 수 없고, 보유한 금액보다 큰 값을 뺄 수도 없습니다.

다만 유효한 결제 금액이라도 보유 포인트 잔액보다 클 수 있습니다. **값 하나의 유효성**과 **여러 값 사이의 관계**는 다른 규칙이므로, `PointBalance.pay(amount)`는 잔액과 결제액의 관계를 지키며 차감해야 합니다.

- **잔액**: 0원도 유효합니다.
- **충전 요청**: 0원은 충전이 아니므로 양수여야 합니다.
- **충전 후 잔액**: 잔액과 충전액이 각각 유효해도 합계가 저장 타입의 표현 범위를 넘지 않아야 합니다.

`Money`가 음수만 거절한다고 충전 규칙까지 완성되는 것은 아닙니다. **공통 값의 유효성**과 **특정 행동의 입력 조건**을 구분해야 합니다.

- QNA · 모든 값과 행동을 별도 객체로 분리해야 할까요?

  모든 문자열이나 숫자를 반드시 VO로 감쌀 필요는 없습니다. 의미가 혼동되거나 유효성 검사가 반복되는 곳에서 도입할 이유를 찾습니다.

  단순한 규칙은 Entity의 행동으로 충분할 수 있습니다. 모든 행동을 도메인 서비스로 옮기기보다, 한 객체가 자연스럽게 책임질 수 있는 규칙인지 먼저 판단합니다.


## 🧪 TDD: 테스트로 확인하는 설계

> **TDD(Test-Driven Development)**는 기대 동작을 테스트로 먼저 표현하고, 실패 → 최소 구현 → 구조 개선을 반복하는 개발 방식입니다.
>

완성한 코드에 나중에 테스트를 붙이는 순서와 다릅니다. 먼저 테스트가 **의도한 이유로 실패하는지** 확인한 뒤 통과시키는 최소 구현을 합니다. 이후 동작을 유지하면서 구조를 다듬습니다.

### 🧪 Red → Green → Refactor

재고 5개에서 6개를 차감하는 규칙을 예로 들어 보겠습니다. 먼저 입력과 기대 결과를 정합니다.

```java
@Test
void rejectsQuantityGreaterThanStock() {
    var stock = new Stock(5);

    assertThrows(IllegalArgumentException.class, () -> stock.decrease(6));
    assertEquals(5, stock.remaining());
}
```

테스트는 “예외가 발생한다”뿐 아니라 **거절 후 재고가 5개로 유지된다**는 기대도 표현합니다.

- Kotlin · 같은 재고 규칙의 테스트

  Kotlin에서도 같은 입력과 기대 결과를 확인합니다.

    ```kotlin
    @Test
    fun rejectsQuantityGreaterThanStock() {
        val stock = Stock(5)
    
        assertThrows<IllegalArgumentException> { stock.decrease(6) }
        assertEquals(5, stock.remaining())
    }
    ```


위 예제의 테스트 annotation과 assertion은 **JUnit Jupiter**를 사용합니다. 아직 타입이 없다면 필요한 생성자·메서드부터 선언합니다. 컴파일이 된 다음, 아무 검사 없이 차감하는 구현이 테스트를 실패시키는지 확인합니다. DB 연결 실패나 잘못된 테스트 이름 때문에 실행하지 못한 것은 이 규칙의 Red가 아닙니다.

| 단계 | 실제로 할 일 | 주의할 점 |
| --- | --- | --- |
| **Red** | 재고 부족을 거절하고 기존 값이 유지된다는 테스트를 먼저 실행 | 실행되지 않은 테스트를 실패 확인으로 기록하지 않기 |
| **Green** | 해당 규칙을 통과시키는 최소 구현 추가 | 아직 요구하지 않은 범용 재고 엔진을 만들지 않기 |
| **Refactor** | 중복 검사·이름·책임 배치를 개선하고 다시 실행 | 기대값을 바꿔 통과시키는 일을 리팩터링이라고 하지 않기 |

첫 테스트가 통과하면 다른 조건을 한 사례씩 추가합니다.

- `5개에서 2개 차감 → 3개`
- `5개 전량 차감 → 0개`
- `0 이하 수량 거절`

정상 사례가 없으면 **모든 요청을 거절하는 구현**도 첫 테스트를 통과할 수 있습니다. 거절 사례와 정상 사례를 함께 확인해야 하는 이유입니다.

이 과정을 거쳐 얻을 수 있는 구현의 한 모습입니다.

```java
final class Stock {
    private int remaining;

    Stock(int remaining) {
        if (remaining < 0) {
            throw new IllegalArgumentException("초기 재고는 음수일 수 없습니다.");
        }
        this.remaining = remaining;
    }

    void decrease(int quantity) {
        if (quantity <= 0 || quantity > remaining) {
            throw new IllegalArgumentException("차감할 수 없는 수량입니다.");
        }
        remaining -= quantity;
    }

    int remaining() {
        return remaining;
    }
}
```

TDD의 대상은 재고만이 아닙니다. 상품·브랜드의 유효성, 좋아요 관계, 포인트 충전, 주문의 금액·상태처럼 **중요한 도메인 규칙**에도 같은 순서를 적용할 수 있습니다.

Refactor에서는 실제 중복이 있는 검사식을 이름 있는 메서드로 묶거나, 호출자가 직접 계산하던 코드를 `decrease`로 옮길 수 있습니다. 이미 단순한 구조라면 불필요한 인터페이스를 추가하기보다 다른 호출자의 중복을 살펴봅니다.

> **리팩터링은 기대 동작을 유지하면서 구조를 개선하는 일입니다.** 테스트 기대값을 바꿔 실패를 없애는 일이 아닙니다.
>

## 🤝 유스케이스와 객체 협력

유스케이스는 사용자의 목적을 이루기 위한 처리 흐름입니다. 하나의 요청을 끝내기 위해 여러 객체가 필요해도, 모든 객체가 서로의 내부 값을 직접 바꿀 필요는 없습니다.

### 🔄 관리자 변경과 고객 조회

관리자가 상품을 수정한 다음 고객이 조회하는 흐름을 살펴봅시다. 관리자는 수정할 자격이 있어야 하고, 상품은 이름·가격·재고의 유효성을 지켜야 합니다. 고객 조회에서는 상품·브랜드·좋아요 수를 응답으로 조합합니다.

```
관리자 수정 요청 → 접근 확인 → 상품 조회 → 상품의 변경 행동 → 저장
고객 상세 조회   → 상품·브랜드·좋아요 관계 조회 → 조회 결과 조합 → 응답
```

**application은 이 순서를 조율합니다.** 상품 모델이 요청자의 역할이나 JSON 필드명을 알아야 하는 것은 아닙니다. 같은 저장된 상품을 사용하더라도 고객과 관리자는 서로 다른 입력·출력 모델을 가질 수 있습니다.

흐름도에는 설명하려는 판단에 필요한 객체를 표시합니다. 클래스의 모든 호출을 채우는 것보다 **어떤 객체가 어떤 이유로 협력하는지**가 중요합니다.

### 🗑️ Hard delete: 행을 제거하는 삭제

> **Hard delete(물리 삭제)**는 저장된 행 자체를 제거하는 방식입니다.
>

행이 사라지므로 일반 조회에서 별도의 삭제 상태 필터는 필요하지 않습니다. 대신 다른 데이터가 그 행을 참조한다면 **무엇이 함께 영향을 받는지** 확인해야 합니다.

**외래 키**는 다른 행을 가리키는 관계를 DB에서 검사하는 제약입니다. 이 제약이 삭제를 막을 수도 있고, 연결된 행도 함께 지우는 **연쇄 삭제** 설정에 따라 영향 범위가 넓어질 수도 있습니다.

예를 들어 상품을 삭제하면서 좋아요까지 정리할지, 연결된 상품이 있는 브랜드의 삭제를 거절할지는 서로 다른 판단입니다. 저장소의 `delete` 호출 전에 **없애려는 대상과 남겨야 할 관계**를 정해야 합니다.

### 🏷️ Soft delete: 상태로 구분하는 삭제

> **Soft delete(논리 삭제)**는 행을 남기고 `deletedAt` 같은 값으로 삭제 상태를 표시하는 방식입니다.
>

이 방식에서는 행이 존재한다는 사실만으로 사용 가능한 대상이라고 판단할 수 없습니다. 고객 조회와 새 주문에서는 삭제된 상품을 제외해야 합니다. 참조가 남아 있어도 **그 대상을 사용할 수 있는지**는 업무 규칙으로 확인합니다.

| 비교할 점 | **🗑️ Hard delete** | **🏷️ Soft delete** |
| --- | --- | --- |
| 데이터 제거 여부 | 행 자체를 제거함 | 행은 남기고 삭제 상태를 표시함 |
| 조회 조건 | 제거된 행은 조회되지 않음 | 사용 가능한 대상을 고르는 삭제 상태 조건이 필요함 |
| 참조에 미치는 영향 | 외래 키·연쇄 삭제 설정과 연결된 데이터를 확인함 | 참조는 남을 수 있지만 사용 가능 여부를 별도로 판단함 |
| 선택할 상황 | 행을 실제로 제거해야 하고 연결된 관계를 정리할 수 있을 때 | 행을 남긴 채 사용 대상에서 제외할 이유가 있을 때 |

**삭제 방식은 기능의 의미와 참조 관계에 따라 선택합니다. 논리 삭제가 모든 기능의 필수 구현 방식인 것은 아닙니다.**

브랜드의 삭제 조건으로 “삭제되지 않은 상품이 남으면 거절한다”를 정했다면 재고가 0인 상품도 확인해야 합니다. 연결 상품을 조회하는 일은 application이 조율하고, 삭제 가능 여부와 변경 행동은 책임에 맞게 배치합니다. **관계를 확인하는 일과 데이터를 바꾸는 행동**을 구분하면 두 삭제 방식에서도 객체 간 협력을 설명할 수 있습니다.

### 💰 포인트 충전과 주문 확정

고객은 충전 API로 자신의 포인트를 늘리고 잔액 API로 확인합니다. 주문은 그 **저장된 잔액**으로 결제합니다. 여러 상품을 주문하려면 상품, 재고, 사용자 포인트, 주문이 함께 협력해야 합니다.

주문 생성과 확정을 구분하면 각 단계가 언제 값을 정하고 변경하는지 명시할 수 있습니다. 이 사례에서 생성한 주문은 확정 전 상태이며, 본인 주문을 확정하면 결제 결과가 있는 확정 상태로 바뀝니다. **생성할 때 차감하지 않고, 확정할 때 차감**합니다.

- **재고**: 수량의 유효성과 보유량을 확인합니다.
- **포인트**: 잔액과 차감액의 관계를 지킵니다.
- **주문**: 품목·금액·상태와 결제 결과를 저장합니다. 결제 수단은 포인트이며, 상품이 사용자 잔액까지 직접 변경하지 않습니다.
- **application**: 필요한 모델을 조회하고 행동·저장을 조율합니다. Entity가 repository나 HTTP DTO를 알 필요는 없습니다.

주문 생성에서는 없거나 삭제된 상품과 잘못된 수량을 거절합니다. 최초 확정에서는 상품이 여전히 존재하며 삭제되지 않았는지, 재고·잔액이 충분한지도 확인합니다. 여러 품목이라면 전체 입력과 필요한 재고·잔액을 확인한 뒤 변경 행동을 호출합니다.

주문에는 품목·수량·단가·합계를 담고, 확정할 때 결제액·포인트 결제 결과를 저장합니다. 예를 들어 포인트 10,000원을 충전한 뒤 합계 7,000원인 주문을 확정했다면, 결제액 7,000원과 남은 잔액 3,000원을 저장하고 다시 조회해 확인합니다.

**입력 검증, 객체의 행동, 저장·조회가 하나의 정상 주문 흐름으로 이어져야 합니다.**

## 🏗 레이어드 아키텍처와 DIP

### 📁 패키지·계층·모듈

세 가지는 서로 다른 경계입니다.

- **패키지**는 클래스의 이름과 위치를 묶습니다. 폴더만 나눠서는 의존이 차단되지 않습니다.
- **계층**은 HTTP 처리·유스케이스·업무 규칙·저장 구현처럼 책임의 종류를 구분합니다.
- **모듈**은 빌드와 의존 설정의 경계입니다. 더 강한 분리와 함께 설정·공개 API 관리 비용도 생깁니다.

starter의 layer-first 구조에서는 계층별 패키지 아래에 기능을 배치합니다.

```
interfaces/api/product     → application/product → domain/product
interfaces/api/admin/...   → application/...
infrastructure/product     ─────────────────────→ domain/product
```

| 계층 | 맡는 일 | 직접 의존하지 않을 것 |
| --- | --- | --- |
| **interfaces** | 고객·관리자 입력과 응답, HTTP 오류 매핑 | infrastructure 저장 구현 |
| **application** | domain의 행동·저장 약속을 이용한 유스케이스 | controller DTO, infrastructure 구현 |
| **domain** | 상태·규칙, 필요한 repository 약속 | interfaces, application, infrastructure |
| **infrastructure** | repository 약속의 JPA 구현 | HTTP 응답 정책과 중복된 업무 규칙 |

상품·브랜드·좋아요 수를 조합하는 조회 application이 있어도 됩니다. 단순한 응답 조합을 반드시 도메인 서비스로 옮길 필요는 없습니다.

### 🔌 DIP: 저장 기술과 업무 정책의 의존 분리

> **DIP(Dependency Inversion Principle)**는 높은 수준의 정책이 저장 기술의 세부 구현에 끌려가지 않도록, 양쪽이 필요한 추상화에 의존하게 하는 원칙입니다.
>

```java
// domain/product: 상품 조회에 필요한 저장 약속
public interface ProductRepository {
    Product find(long productId);
}

// application/product: 상품 조회 유스케이스가 ProductRepository를 주입받는다.
// infrastructure/product: JpaProductRepository가 이 약속을 구현한다.
```

실행 중 application이 호출하는 객체는 JPA 구현체일 수 있습니다. 하지만 소스에서는 그 구현체 이름을 몰라도 됩니다. 테스트에서는 DB 없이 약속한 값을 돌려주는 **테스트용 구현(fake)**을 연결할 수 있습니다.

**런타임 호출 방향과 소스의 타입 의존 방향은 다릅니다.** 실행 시 JPA를 호출한다는 사실만으로 application이 JPA 구현 타입에 직접 의존해야 하는 것은 아닙니다.

인터페이스가 domain에 있어도 반환 타입이 controller DTO라면 경계가 새어 나갑니다. 이름과 폴더뿐 아니라 **메서드의 입력·출력 타입**도 살펴야 합니다. 모든 클래스에 인터페이스를 붙이는 것이 DIP의 목적은 아닙니다.

- QNA · JPA annotation이 있으면 모델을 모두 분리해야 할까요?

  starter의 `ExampleModel`에는 DB 매핑을 표시하는 JPA annotation이 있습니다. DB 매핑만 맡는 별도 persistence 모델로 분리하면 저장 기술과의 경계를 더 엄격하게 만들 수 있지만, 모델 간 변환과 관리 비용도 생깁니다.

  모든 모델에서 annotation을 제거하는 일과, 정한 패키지 의존을 지키는 일은 다른 선택입니다. 기존 구조에서 시작할 때 패키지 규칙을 갑자기 “모든 프레임워크 금지”로 넓힐 필요는 없습니다.


### 🗂️ Layer-first와 Feature-first

| 구성 | 찾기 쉬운 것 | 함께 고려할 비용 |
| --- | --- | --- |
| **🧱 Layer-first** | 계층별 책임과 같은 종류의 코드 | 한 기능을 고칠 때 여러 폴더를 오감 |
| **🧩 Feature-first** | `order/domain`, `order/application`처럼 한 기능의 변경 | 기능 사이의 공개 경계와 의존을 정해야 함 |

폴더 구성을 바꾸는 것만으로 실제 의존이 정리되지는 않습니다. 어떤 구조를 쓰든 **무엇에 의존해도 되는지와 그 이유**를 설명할 수 있어야 합니다.

## 🤖 AI 협업과 실행 가능한 규칙

AI와의 협업은 **설계 구체화**와 **작은 기능 구현**으로 이어집니다. 초안을 놓고 책임과 의존을 질문한 뒤, 선택한 구조 안에서 코드를 구현합니다.

예를 들어 `Product`가 상품 규칙뿐 아니라 브랜드·좋아요 조회와 응답 조합까지 맡는 초안을 만들었다고 합시다. AI에 다음과 같이 질문할 수 있습니다.

> **이 설계에서 책임이 겹치는 부분과 변경에 취약한 의존을 찾아줘. 대안 두 가지의 비용을 비교하고, 결정되지 않은 정책은 먼저 질문해줘.**
>

AI가 상품 안에서 조합하는 안과 application에서 조합하는 안을 제안했다면, 책임과 변경 비용으로 비교합니다.

- **Product에서 조회·조합**: 호출을 한곳에 모을 수 있지만 조회·응답의 변경이 상품 모델에 영향을 줍니다.
- **application에서 조회·조합**: 조회를 조율하는 코드가 필요하지만 상품 객체는 자신의 상태·규칙에 집중할 수 있습니다.

“브랜드 응답이 바뀔 때 어느 객체가 바뀌는가?”라는 반례를 두 안에 대입해 봅니다. 이 사례에서는 조회 조합을 application에 두는 선택을 할 수 있습니다. 선택한 이유와 남은 질문을 설계에 반영합니다.

책임과 기본 계약이 정리되면 좋아요 등록·취소처럼 **작은 기능을 하나씩** 요청합니다. 규칙과 기대값을 정하고, AI가 제안한 코드의 diff와 실행 결과를 확인합니다.

> **AI와 협업할 때도 제품 정책과 정답의 책임은 사람에게 있습니다.** 구현과 그 구현을 평가할 기대값을 동시에 맡기지 않습니다.
>

다음은 좋아요 기능 하나를 요청하는 예시입니다.

```
이번 기능: 상품 좋아요 등록·취소
정책: 한 사용자와 한 상품 사이의 좋아요 관계는 하나만 저장한다.
구조: domain은 application·interfaces·infrastructure에 의존하지 않는다.
허용 변경: 좋아요 기능과 관련 테스트. 전체 패키지를 바꾸지 않는다.
작업: 변경할 책임을 설명한 뒤 작은 단위로 구현한다.
검증: 관련 테스트, lint, ArchitectureTest를 실행하고 결과를 확인한다.
금지: 기대값·테스트·lint·ArchUnit 규칙을 승인 없이 삭제하거나 완화하지 않는다.
```

**기능·정책·허용 변경·검증·금지 사항**을 함께 전달하면, AI의 제안이 설계 의도 안에 있는지 판단하기 쉬워집니다. TDD에서도 먼저 정상·오류 기대값을 정하고 Red를 확인한 뒤 최소 구현을 요청할 수 있습니다. AI가 다른 정책을 제안하면 코드에 반영하기 전에 그 제안을 판단합니다.

### 🛠️ lint·ArchUnit·동작 테스트의 역할

| 도구 | 확인하는 것 | 대신 판단하지 못하는 것 |
| --- | --- | --- |
| **Formatter** | 공백·들여쓰기 같은 표현 | 업무 규칙 |
| **lint** | 정한 스타일·정적 규칙 | 주문 금액의 제품 의미 |
| **컴파일러** | 문법·타입·참조 | 허용해야 할 의존 방향 |
| **ArchUnit** | 컴파일된 클래스의 패키지·타입 의존 | 좋은 객체 책임의 모든 측면 |
| **동작 테스트** | 특정 입력의 기대 결과 | 작성하지 않은 모든 경우 |

domain 코드가 controller DTO를 사용해도 컴파일은 성공할 수 있습니다. 그 의존을 금지하는 ArchUnit 테스트는 실패해야 합니다. 반대로 모든 구조 검사를 통과해도 차감 금액을 잘못 계산할 수 있으므로 도메인 테스트가 필요합니다.

**ArchUnit은 JVM bytecode(컴파일 결과물)를 검사하는 표준 라이브러리**이며 Java·Kotlin 코드에 사용할 수 있습니다. 직접 import 문자열 검사기를 만드는 것과는 다릅니다. 연결 예시에 실제 패키지와 소수의 핵심 의존 규칙을 적용하고, 각 규칙이 필요한 이유를 설명할 수 있어야 합니다.

<aside>
⚠️

**주의 · 실패한 검사는 원인을 판단해야 합니다.**

검사가 실패하면 코드·설계·검사 중 무엇이 잘못됐는지 판단합니다. **검사 대상을 없애거나 실패를 무시하는 설정은 의존 문제를 고치는 방법이 아닙니다.**

</aside>

### ⚙️ 로컬 검사와 CI

**CI는 저장소에 제출한 코드에 검사를 자동으로 실행하는 환경입니다.** 로컬과 같은 검사 명령을 사용하면 구현 중 확인한 결과를 제출한 코드에서도 재현할 수 있습니다.

- **구현 중**: 바꾼 기능의 테스트로 빠르게 피드백을 받습니다.
- **기능을 마무리할 때**: lint·ArchUnit과 필요한 테스트를 함께 실행합니다.
- **CI에서 실패하면**: 실패한 입력·규칙·실행 환경을 확인해 원인을 찾습니다.

언어별 연결 설정과 실행 명령은 과제에서 확인합니다.

## 🔎 책임 경계와 테스트

테스트는 확인하려는 책임의 경계에 둡니다. 모든 규칙을 HTTP부터 반복하면 실행 비용과 실패 원인 추적 비용이 커질 수 있습니다.

| 확인할 질문 | 적절한 테스트 |
| --- | --- |
| 수량·충전액이 유효하고 재고·잔액 부족을 거절하는가? | Spring·DB 없는 **domain 단위 테스트**, 대표 규칙은 TDD |
| 요청자 구분·브랜드 삭제 조건·객체 협력이 맞는가? | fake를 이용한 **application 테스트** |
| 충전 잔액·선택한 삭제 방식·주문 품목·결제 결과가 DB에 반영되고 다시 읽히는가? | 실제 repository·DB **통합 테스트** |
| 고객·관리자 요청이 올바른 입력·응답·오류로 연결되는가? | CRUD·포인트·주문과 요청자 구분을 확인하는 **HTTP 테스트** |

저장 테스트에서 같은 메모리 객체만 읽으면 빠진 매핑을 놓칠 수 있습니다. JPA라면 `flush()`로 변경을 DB에 보내고 `clear()`로 관리 중인 객체를 비운 뒤 재조회합니다. 이렇게 **저장된 값**이 다시 읽히는지 확인합니다. 수량의 모든 경계값을 HTTP 테스트에 똑같이 반복할 필요는 없습니다.

### 🔐 로컬 실습의 요청자 구분

이번 실습에서는 모의 사용자·관리자 요청으로 기본 기능의 접근 범위를 확인합니다.

- **관리자 요청**: 관리자 기능은 허용하고 일반·식별 없는 요청은 거절합니다.
- **고객 요청**: 자신의 좋아요·포인트·주문을 다루는지 해당 유스케이스에서 확인합니다.
- **조회 범위**: 고객은 내 주문을, 관리자는 구매자들의 주문을 조회합니다.

**모의 식별은 로컬 실습에만 사용하고 서버를 외부에 공개하지 않습니다.** 실제 실행에 필요한 지원 설정은 과제의 참고 접기에서 사용합니다.
