## 💻 Implementation Quest

> **설계를 구체화하고, AI와 기본 기능을 구현합니다.**
고객·관리자의 요청을 **HTTP → application → domain → repository·DB → 응답**까지 연결합니다.
>

1주차에 사용한 Java 또는 Kotlin starter 저장소에서 이어서 작업합니다. Example 테스트와 요구·오류 계약 정리 방식을 참고해, **이번 구현과 테스트의 대상인 아래 기본 기능**의 계약을 정하고 구현합니다.

### 📐 1. 설계

다음 내용을 하나의 설계 문서에 정리합니다.

| 표현할 것 | 담을 내용 |
| --- | --- |
| 버드뷰 | 고객·관리자, API 서버, DB와 요청 방향 |
| 구조와 의존 | interfaces / application / domain / infrastructure의 역할과 허용 방향 |
| 도메인 관계 | Brand–Product, User–Like–Product, Order–OrderItem과 재고·포인트의 책임 |
| 대표 흐름 | 관리자 변경→고객 조회, 좋아요 등록·취소, 포인트 충전→주문 확정 중 선택한 흐름 |

기본 API의 **method/path/입력/성공/대표 오류**와 주요 규칙의 기대값을 함께 적습니다.

**AI와 설계 다듬기** — 초안을 만든 뒤 책임 중복과 의존을 질문하고, 대안을 비교해 선택한 이유를 정리합니다.

> **이 설계에서 책임이 겹치는 부분과 변경에 취약한 의존을 찾아줘. 대안 두 가지의 비용을 비교하고, 결정되지 않은 정책은 먼저 질문해줘.**

AI가 제안한 대안에 “브랜드 응답이 바뀌면 어떤 객체까지 바뀌는가?” 같은 반례를 대입합니다. 상품의 상태·규칙과 조회 결과 조합을 어디에 둘지 결정하고, 구현하며 바뀐 판단은 문서에 반영합니다.

### 🔧 2. 개발 규칙 설정

**Java는 Checkstyle, Kotlin은 기존 ktlint**를 사용합니다. **표준 ArchUnit**을 기존 JUnit 테스트에 연결하고, 설계에서 정한 패키지 의존 규칙을 검사합니다.

사용하는 언어의 lint 설정과 ArchUnit 예시를 적용한 뒤 관련 테스트를 실행합니다.

- Java · Checkstyle 연결

  JDK 21과 기존 Gradle·Spring Boot 버전을 사용합니다. `apps/commerce-api/build.gradle.kts`의 기존 `plugins`에 `checkstyle`을 합치고 설정을 추가합니다.

    ```kotlin
    plugins {
        checkstyle
    }
    
    checkstyle {
        toolVersion = "10.26.1"
        configFile = rootProject.file("config/checkstyle/checkstyle.xml")
        isIgnoreFailures = false
        maxWarnings = 0
    }
    ```

  저장소 루트의 `config/checkstyle/checkstyle.xml`에 다음 규칙을 추가합니다.

    ```xml
    <?xml version="1.0"?>
    <!DOCTYPE module PUBLIC
        "-//Checkstyle//DTD Checkstyle Configuration 1.3//EN"
        "https://checkstyle.org/dtds/configuration_1_3.dtd">
    <module name="Checker">
        <module name="TreeWalker">
            <module name="AvoidStarImport"/>
            <module name="UnusedImports"/>
        </module>
    </module>
    ```

  이 설정은 해당 모듈의 Java main·test 소스를 검사하고 `check`에 연결됩니다. 다른 모듈에도 코드가 있다면 검사 범위를 연결합니다. Gradle Checkstyle 안내

### 📋 3. 기본 기능 구현

대표 도메인 규칙 하나를 골라 **TDD**를 적용합니다. 예를 들어 재고 5개에서 6개 차감은 거절하고, 2개 차감 후에는 3개가 남는지 확인합니다.

1. **Red** — 정상·대표 오류의 기대값을 테스트로 작성하고 의도한 실패를 확인합니다.
2. **Green** — 테스트를 통과시키는 최소 구현을 만듭니다.
3. **Refactor** — 중복·이름·책임을 다듬고 테스트를 다시 실행합니다.

이후 AI와 **작은 기능을 하나씩 구현**합니다. 변경 diff와 관련 테스트 결과를 확인한 뒤 다음 기능으로 넘어갑니다.

아래 API의 입력·성공 결과·대표 오류를 설계 문서와 테스트에 연결합니다.

**🏷 상품·브랜드·좋아요**

| 기능 | 구현할 것 | 핵심 조건 |
| --- | --- | --- |
| 브랜드 상세 | `GET /api/v1/brands/{brandId}` | 존재하며 삭제되지 않은 브랜드 조회 |
| 상품 목록·상세 | `GET /api/v1/products`, `GET /api/v1/products/{productId}` | 브랜드 정보·좋아요 수 포함 |
| 상품 목록 조건 | 브랜드 필터·페이지 조회, `latest`·`price_asc`·`likes_desc` 정렬 | 동률의 보조 정렬 기준과 잘못된 입력 처리 |
| 좋아요 등록·취소 | `POST/DELETE /api/v1/products/{productId}/likes` | 사용자–상품 관계로 저장, 중복 관계 방지 |
| 내 좋아요 목록 | `GET /api/v1/users/{userId}/likes` | 자신의 관계만 조회·취소, 상품의 좋아요 수에 반영 |
- 좋아요 수는 관계에서 조회합니다. 삭제된 상품은 새 좋아요와 내 목록에서 제외하고, 남아 있는 자신의 좋아요 관계는 취소할 수 있게 합니다.
- 없거나 삭제된 대상의 고객 상세 조회는 없는 대상 오류로 처리합니다.

**💰 포인트·주문**

| 기능 | 구현할 것 | 핵심 조건 |
| --- | --- | --- |
| 내 포인트 충전 | `POST /api/v1/points/charge` | `amount`를 잔액에 더해 DB에 저장하고 충전 후 잔액 반환 |
| 내 잔액 조회 | `GET /api/v1/points` | 요청자로 식별한 사용자의 저장된 잔액 조회 |
| 주문 생성 | `POST /api/v1/orders` | 여러 품목·수량·단가·합계를 DRAFT로 저장, 생성 시 차감 없음 |
| 주문 확정 | `POST /api/v1/orders/{orderId}/confirm` | 본인의 DRAFT 주문을 확정하며 재고·포인트 차감, 결제액·결과를 저장하고 CONFIRMED로 변경 |
| 내 주문 목록·상세 | `GET /api/v1/orders`, `GET /api/v1/orders/{orderId}` | 내 주문의 품목·수량·금액·상태·결제액 조회 |
- **포인트**: 1포인트는 1원입니다. 충전액은 양의 정수로 받고 누락·잘못된 타입·표현 범위 초과를 거절합니다.
- **잔액**: 0원은 허용합니다. 잔액 합산 범위를 확인하고, 충전 입력 오류에는 기존 값을 유지합니다.
- **주문**: DRAFT는 확정 전, CONFIRMED는 결제를 마친 상태입니다. 생성·확정 시 상품의 존재·삭제 여부와 양수 수량을 확인하고, 확정 시 재고·잔액 부족을 거절합니다. 중복 상품 품목은 합산하거나 거절하고 총수량으로 재고를 확인합니다.

실습용 사용자는 fixture(테스트용 데이터)로 준비할 수 있습니다. 포인트 충전과 주문은 위 API로 구현합니다.

**🛠 관리자**

| 기능 | 구현할 것 | 핵심 조건 |
| --- | --- | --- |
| 브랜드 전체 CRUD | `GET/POST /api-admin/v1/brands`, `GET/PUT/DELETE /api-admin/v1/brands/{brandId}` | 유효한 브랜드 정보 저장·조회, 연결된 상품의 삭제 조건 확인 |
| 상품 전체 CRUD | `GET/POST /api-admin/v1/products`, `GET/PUT/DELETE /api-admin/v1/products/{productId}` | 존재하며 삭제되지 않은 브랜드 참조, 정한 이름·가격 범위 검증, 수정 시 브랜드 유지 |
| 상품 재고 변경 | `PUT /api-admin/v1/products/{productId}/stock` | 0 이상인 최종 수량 설정 |
| 주문 목록·상세 | `GET /api-admin/v1/orders`, `GET /api-admin/v1/orders/{orderId}` | 구매자별 주문의 품목·상태·금액·결제 결과 조회 |

관리자 변경을 고객 조회에 반영하고, 고객·관리자에게 제공할 응답 필드를 구분합니다.

**기본 삭제 조건**

- 삭제되지 않은 상품이 연결된 브랜드의 삭제는 거절합니다. 재고 0인 상품도 포함합니다.
- 삭제된 브랜드·상품은 고객 조회·새 주문에서 제외합니다. 수정·재고 변경의 대상으로도 사용하지 않습니다.
- 기존 참조가 깨지거나 저장된 주문 정보가 함께 지워지지 않도록 물리 삭제·논리 삭제 중 알맞은 방식을 선택하고 설계에 이유를 적습니다.

- Java · 관리자 접근 지원 설정

  main 소스의 `com.loopers.config`에 추가합니다. 의존성과 실행 예시는 아래 공통 접기를 사용합니다.

    ```java
    package com.loopers.config;
    
    import org.springframework.context.annotation.Bean;
    import org.springframework.context.annotation.Configuration;
    import org.springframework.security.config.annotation.web.builders.HttpSecurity;
    import org.springframework.security.web.SecurityFilterChain;
    
    @Configuration
    public class AdminBoundaryConfig {
        @Bean
        SecurityFilterChain adminBoundary(HttpSecurity http) throws Exception {
            return http.securityMatcher("/api-admin/**")
                .authorizeHttpRequests(rules -> rules.anyRequest().hasRole("ADMIN"))
                .exceptionHandling(errors -> errors.authenticationEntryPoint(
                    (request, response, exception) -> response.sendError(403)))
                .build();
        }
    }
    ```

- 공통 · 관리자 HTTP 테스트 실행

  `apps/commerce-api/build.gradle.kts`의 기존 `dependencies`에 추가합니다. 버전은 기존 Spring Boot 의존성 관리를 사용합니다.

    ```kotlin
    implementation("org.springframework.boot:spring-boot-starter-security")
    testImplementation("org.springframework.security:spring-security-test")
    ```

  MockMvc는 서버 포트를 열지 않고 애플리케이션의 HTTP 요청 처리를 실행하는 테스트 도구입니다. 기존 DB fixture와 `@SpringBootTest`, `@AutoConfigureMockMvc`를 사용하고 기본 필터를 유지합니다. 다음 Java 테스트 본문은 관리자 허용과 일반·미식별 요청 거절을 확인합니다.

    ```java
    // 정적 import: MockMvcRequestBuilders.get, MockMvcResultMatchers.status,
    // SecurityMockMvcRequestPostProcessors.user
    mvc.perform(get("/api-admin/v1/brands").with(user("admin").roles("ADMIN")))
        .andExpect(status().isOk());
    mvc.perform(get("/api-admin/v1/brands").with(user("customer").roles("USER")))
        .andExpect(status().isForbidden());
    mvc.perform(get("/api-admin/v1/brands"))
        .andExpect(status().isForbidden());
    ```

  POST·PUT·DELETE 테스트에는 `SecurityMockMvcRequestPostProcessors.csrf()`를 함께 넣습니다. 거절 테스트에도 유효한 CSRF 입력을 사용해 요청자 구분을 확인합니다.

  이 지원 설정은 관리자 경로에 적용되며 네트워크용 관리자 로그인은 제공하지 않습니다. 테스트 입력 안내, CSRF 입력 안내


각 기능의 **정상 경로와 대표 오류**를 확인합니다.

| 테스트 경계 | 확인할 것 |
| --- | --- |
| domain·application | 규칙의 기대값, 객체 협력과 요청자 구분 |
| repository·DB | 저장 후 재조회한 값과 관계. JPA는 `flush/clear` 후 확인 |
| HTTP | 실제 API 응답과 저장 동작, 입력·접근 거절 시 기존 값 유지 |

연결 흐름으로 **충전 API → 여러 품목 주문 확정 → 내 주문·잔액 조회**를 확인합니다. 잔액 0에서 10,000원을 충전하고 7,000원을 결제했다면 잔액은 3,000원입니다.
